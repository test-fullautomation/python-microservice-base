A Python + C++ framework for building gRPC microservices with Consul-based service discovery and Nomad-based orchestration. The Manager GUI gives you a desktop UX over the FastAPI bridge: start/stop infrastructure agents, browse registered services, invoke methods via gRPC reflection, and scaffold new services from a 4-step wizard.

Getting Started

Microservice Manager is a graphical interface for operating and building MicroserviceBase services. It runs in two modes (Electron desktop or browser), connects to the same FastAPI bridge, and gives you three top-level workspaces.

Dual Hosting

The GUI runs in two modes:

  • Electron — standalone desktop app with native window, system tray, and auto-launch of the FastAPI bridge.
  • Browser — served by the FastAPI bridge at http://localhost:1112; no installation required (just python -m MicroserviceBase.adapters.ui_bridge.fastapi_bridge and open the URL).

Both modes share the same web front-end and connect to the same FastAPI bridge.

Three Modes

Use the mode toggle buttons in the top navigation bar:

  • Services — browse Consul-registered services, invoke gRPC methods via reflection.
  • Service Network — start / stop / inspect Consul and Nomad agents; browse jobs; submit new .nomad.hcl files.
  • Service Creator — 4-step wizard to scaffold a new service project (proto + domain + adapter + clients + Nomad HCL).

Status pills in the navbar

To the right of the mode toggle, three small pills show live infrastructure health:

  • Bridge — the FastAPI bridge process. ▶/■ buttons start/stop it (Electron mode).
  • Consul — service-discovery agent. Click to jump to the Consul tab in Service Network.
  • Nomad — orchestrator agent. Click to jump to the Nomad tab.

LEDs are polled every 5 seconds and reflect the bridge's /api/{consul,nomad}/health endpoints.

Service Network (Consul + Nomad)

The Service Network mode replaces the per-terminal consul agent -dev / nomad agent -dev workflow. Two sub-tabs:

Consul tab

Two render states:

  • Setup form (agent stopped) — three start modes: Dev Mode (single-node in-memory), Config Directory (load .hcl / .json), or Connect to Existing (point at a running agent's URL).
  • Connected dashboard (agent running) — cluster leader, node count, registered services list (this is the live source of truth used by gRPC clients with useConsul=true), plus Open Consul UI / Disconnect / Stop Agent buttons.

Defaults match the framework: HTTP port 8500, datacenter dc1, bind 0.0.0.0.

Nomad tab

Same two-state pattern. Once running:

  • Counters — Total Jobs / Running / Pending / Dead / Nodes Ready.
  • Jobs table — every submitted job with type, status, task groups; per-row link to detail view.
  • Submit Job dialog — HCL/JSON toggle, "Load from file…" picks a generated deploy/<svc>.nomad.hcl, or paste content directly.
  • Open Nomad UI — opens the bundled Nomad UI (:4646/ui) in a new browser window.

Dev Mode start automatically writes a raw_exec-enabled config so generated services using driver = "raw_exec" work on Windows.

For the full walkthrough with per-state screenshots, see Operating Consul + Nomad.

Services Mode

The default mode. Sidebar lists every Consul-registered service. Click a service to load its panel in the content area.

Sidebar Navigation

  • The search bar at the top filters services by name.
  • Services show a status icon — green for healthy (passing Consul health check), red for failing.
  • When connected to multiple Consul clusters, services are grouped under collapsible cluster headers.

Method Invocation (via gRPC reflection)

Click a service to open its panel. The Manager GUI uses the server's gRPC reflection to enumerate the available methods, then renders one accordion item per method — a JSON textarea pre-filled from the request schema, a Call button, and a response area.

Reflection-not-available fallback

Some servers (e.g. older builds, custom toolchains) don't ship grpc++_reflection. When that happens the bridge falls back to compiling local .proto files via grpc_tools.protoc. If the bridge can't find any local protos, the panel shows a folder-path input so you can point it at the right directory. The path is remembered for the rest of the browser session.

Service GUI Plugins

Each service can ship a custom GUI plugin (HTML + JS) loaded from web/services/<ServiceName>/. When present, the plugin replaces the default reflection-based invoker with a service-tailored UI — e.g. a Cleware switch service can render a board with toggles instead of a generic method list. Plugins use the same MM.serviceClient API to talk to the bridge.

Service Creator

Switch to Service Creator mode for a 4-step wizard that scaffolds a new service project (proto + domain + adapter + clients + Nomad HCL) without writing boilerplate.

The four steps

  1. Basic Info — name, language (C++ / Python), GUI variant (none / widget / qml / wasm / html).
  2. Technology — toolchain matrix. For C++: server uses MSYS2 grpc or vcpkg+QtMinGW grpc; client picks a matching gRPC stack (Google grpc++ via MSYS2, Qt6::Grpc, or Google grpc++ via vcpkg).
  3. Methods — define RPC methods manually, or click Import .proto… to parse an existing file (handles multi-service protos with a picker; offers single-project vs monorepo output layout).
  4. Review & Generate — preview the file tree before writing. Output goes to the path you pick.

Same backend as mb-scaffold CLI

The wizard is a thin frontend over the same generator that mb-scaffold calls. For CI / scripted use, drive the same generator from a YAML file: python -m MicroserviceBase.tools.scaffold_cli -c spec.yaml.

For the full walkthrough with per-step screenshots and the YAML config schema, see Service Creator wizard.

Settings

  • Bridge URL — where the FastAPI bridge runs (default http://127.0.0.1:1112). Override via the MB_BRIDGE_URL env var.
  • Default Consul URL — pre-fills the Consul tab and the Connect dialog (default http://127.0.0.1:8500).
  • Theme — light / dark / auto.

Troubleshooting

Quick lookups. For the full symptom-indexed reference see repo: docs/troubleshooting.html.

Bridge LED stays red

Bridge process didn't start. In Electron mode click ▶ next to the LED. If port 1112 is taken, free it (netstat -ano | findstr :1112) or set MB_BRIDGE_URL to a different port.

"Reflection RPC … failed: UNIMPLEMENTED" when clicking a service

The server doesn't ship grpc++_reflection. The panel offers a proto-path input field — type the folder containing the service's .proto and click Use this path. Permanent fix: rebuild the server with reflection enabled (the latest vcpkg overlay-port forces this; re-run init_vcpkg_overlay.bat --upgrade).

Service registers, then disappears from Consul ~30 seconds later

Consul TCP health check is failing. Check nomad alloc logs <alloc-id> — service likely crashed or never started gRPC. Confirm <PREFIX>_GRPC_PORT was set in the env (Nomad sets it via ${NOMAD_PORT_grpc}).

Nomad job stays "pending" forever

Driver mismatch most often. Generated jobs use raw_exec; dev mode auto-enables it. Custom config? Add the raw_exec plugin block. Or check nomad node status for any healthy clients.

"Port 8500 in use" when starting Consul (or 4646 for Nomad)

Another agent is running. Either stop it (tasklist | findstr consul → taskkill /pid <pid>) or use the tab's Connect to Existing form to point at it.
