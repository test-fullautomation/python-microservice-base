Quick Start

Install MSYS2 → pacman -Syu twice → install the compiler + packages → run build_deploy_msys2.bat.

Total time: ~20 minutes, most of it downloading. 
# One-liner after MSYS2 is installed and updated:
pacman -S --needed --noconfirm \
    mingw-w64-x86_64-gcc \
    mingw-w64-x86_64-gdb \
    mingw-w64-x86_64-cmake \
    mingw-w64-x86_64-ninja \
    mingw-w64-x86_64-grpc \
    mingw-w64-x86_64-protobuf \
    mingw-w64-x86_64-curl \
    mingw-w64-x86_64-qt6-base \
    mingw-w64-x86_64-qt6-tools

Why MSYS2 for MinGW on Windows?

MinGW itself is just a compiler. You still need a package manager to install the libraries your code depends on — gRPC, Protobuf, curl, Qt. For MinGW on Windows there are realistically three options:

OptionOutcome
vcpkg + x64-mingw-dynamic triplet Community-tier. Ports break often (openssl, protobuf, grpc). First-time install: 20–60 min of source compile, many retries.
Build gRPC/Qt/etc. from source manually Works. Takes a full day per version upgrade. Not recommended.
MSYS2 via pacman Prebuilt binaries. Installs in minutes. Maintained.
MSYS2 is the native MinGW-w64 ecosystem on Windows. Its pacman repository ships thousands of MinGW libraries — the same ones most open-source C++ projects on Windows use. You install MSYS2 once, then use it as a library host; your day-to-day work still happens in plain Windows cmd.

MinGW vs. MSVC — what's the honest difference?

A common misconception is that "MinGW makes Windows apps run like Linux apps." That's not true. MinGW-compiled binaries are 100% native Windows PE executables. They call CreateFile, WaitForSingleObject, all the normal Win32 APIs, just like an MSVC build does. Windows has no idea they came from GCC.

What MinGW actually is: a GCC compiler + GNU C++ runtime ported to Windows. The compiler has Unix heritage; the output binary does not.

Where the size difference comes from

MSVCMinGW
C / C++ runtime MSVCRT / Universal CRT — ships with Windows 10+ by default GNU libstdc++ — not on Windows; each app must carry it
Runtime DLLs shipped alongside your .exe none (system has them) libstdc++-6.dll (~2 MB)
libgcc_s_seh-1.dll (~100 KB)
libwinpthread-1.dll (~60 KB)
Typical Hello World size overhead baseline +3–5 MB

Other integration trade-offs

AspectMSVCMinGW
Debugging tools Visual Studio / WinDbg / ETW understand MSVC PDB symbols natively; crash dumps "just work" Produces DWARF symbols; needs gdb, or conversion to PDB
Windows SDK + DirectX + commercial SDKs Ship MSVC-compatible libraries by default ABI walls — you can't link MSVC-built libs with MinGW
vcpkg Windows port quality First-class, tested, most ports prebuilt Community-tier; openssl / protobuf / grpc frequently fail to build
GPL / LGPL licensing MSVC runtime is proprietary — not always compatible GNU runtime is GPL-with-exception — sometimes required for LGPL Qt distributions
Summary for end users:
"MinGW is a Linux-style compiler (GCC) that produces Windows binaries. Those binaries are native Windows apps, but they use GNU's C++ runtime — which Windows doesn't include — so every MinGW app ships an extra 3–5 MB of libstdc++ / libgcc / libwinpthread DLLs alongside the exe. MSVC uses Microsoft's runtime which is already part of every Windows install, so MSVC apps ship smaller and integrate more cleanly with the OS."
So why use MinGW at all? A few valid reasons:
  • You don't want to install Visual Studio (6 GB) and want a smaller toolchain (MSYS2 is ~2 GB).
  • You need LGPL-clean Qt redistribution; MinGW's LGPL+exception runtime is simpler to comply with than MSVC's.
  • You already have a MinGW toolchain in CI from cross-platform projects.
  • You're allergic to Microsoft developer tooling.
For everyone else on Windows: use MSVC (build_deploy.bat) and skip the pain.

"I already have Qt for MinGW from the Qt installer — can I skip MSYS2's Qt?"

No. Here's why.

ComponentBuilt with
Qt installer's Qt6 (MinGW kit)MinGW-w64 GCC 11.2.0
MSYS2's mingw-w64-x86_64-grpcMinGW-w64 GCC 15.2.0 (current)

These are different GCC major versions. Linking Qt libs built with GCC 11.2 + gRPC libs built with GCC 15.2 into the same binary is an ABI coin-flip: linker succeeds, runtime blows up inside std::string or std::mutex.

The rule: every library in a single binary must come from one MinGW toolchain. Either Qt installer's GCC 11.2 for everything (hours building grpc from source), or MSYS2's current GCC for everything (minutes of pacman).

Your existing Qt installer install isn't wasted — it stays useful for the MSVC build path (build_deploy.bat points QT_DIR at C:\Qt\<ver>\msvc2019_64). The two kits coexist on the same machine without conflict.

1 Install MSYS2

  1. Download the installer: https://www.msys2.org/ — "Installer: msys2-x86_64-…exe"
  2. Run it. Accept the default path: C:\msys64.
  3. Next → Finish. The installer offers to launch MSYS2 immediately — let it.
If you clicked past the "Run MSYS2 now" checkbox, don't worry — launch it from Start Menu → MSYS2 UCRT64.

A terminal window opens. You'll use it for the next two steps only.

2 First-Time Update (One-Time)

This refreshes MSYS2's package keyring and updates pacman itself. Run these inside the MSYS2 terminal (not plain cmd). 

pacman -Syu --noconfirm

Near the end it may say "close the terminal and reopen it to continue". Do exactly that:

  1. Close the MSYS2 terminal window.
  2. Re-open MSYS2 UCRT64 from the Start Menu.
  3. Run it a second time:
pacman -Syu --noconfirm

Done. You won't need to do this again for future projects.

3 Install Compiler + Libraries

Still inside the MSYS2 terminal:

pacman -S --needed --noconfirm \
    mingw-w64-x86_64-gcc \
    mingw-w64-x86_64-gdb \
    mingw-w64-x86_64-cmake \
    mingw-w64-x86_64-ninja \
    mingw-w64-x86_64-grpc \
    mingw-w64-x86_64-protobuf \
    mingw-w64-x86_64-curl \
    mingw-w64-x86_64-qt6-base \
    mingw-w64-x86_64-qt6-tools

What each package does

PackagePurpose
mingw-w64-x86_64-gccThe C++ compiler (g++.exe) + libstdc++
mingw-w64-x86_64-gdbDebugger (gdb.exe) — used by Qt Creator's F5 debug and command-line crash traces
mingw-w64-x86_64-cmakeBuild-system generator
mingw-w64-x86_64-ninjaFast parallel build driver
mingw-w64-x86_64-grpcgRPC++ runtime + grpc_cpp_plugin for code generation
mingw-w64-x86_64-protobufProtobuf runtime + protoc compiler
mingw-w64-x86_64-curlUsed by ConsulRegistration to talk to Consul
mingw-w64-x86_64-qt6-baseQt 6 Core / GUI / Widgets — for the Widgets GUI client
mingw-w64-x86_64-qt6-toolsQt tools (incl. windeployqt-qt6.exe) for packaging

Tip: if you prefer a single command, mingw-w64-x86_64-toolchain is a meta-package that pulls in gcc, gdb, binutils, and the rest of the core toolchain at once. It adds ~100 MB you probably won't use, so the explicit list above is the lean option.

Expected time: 5–15 minutes. Download size ~500 MB, installed size ~1.5 GB. No compilation — these are prebuilt.

When the prompt returns, close the MSYS2 terminal. You're done with it for this project.

4 Verify the Install

Open a plain Windows cmd (Win+R → cmd → Enter). Run: 

dir C:\msys64\mingw64\bin\g++.exe
dir C:\msys64\mingw64\bin\gdb.exe
dir C:\msys64\mingw64\bin\protoc.exe
dir C:\msys64\mingw64\bin\grpc_cpp_plugin.exe
dir C:\msys64\mingw64\share\grpc

All five should list files (no "File Not Found"). If they do, your MinGW stack is ready. Check the debugger runs: 

C:\msys64\mingw64\bin\gdb.exe --version

Should print GNU gdb (GDB) 14.x or newer — that's the binary Qt Creator's kit (step 7b) will point at for F5 debug.

Optional — confirm the compiler version: 

C:\msys64\mingw64\bin\g++.exe --version

You should see something like g++.exe (Rev2, Built by MSYS2 project) 15.2.0.

5 Point the Project at MSYS2

Open your service folder (e.g. examples\SampleService) and edit set_env_msys2.bat. The top line should read: 

set "MSYS2_ROOT=C:\msys64\mingw64"

If you installed MSYS2 somewhere else (rare), change this path to point at the folder that contains bin\g++.exe.

Do not edit set_env.bat — that one is for the MSVC build path and should keep its Visual Studio / vcpkg values. MSVC and MSYS2 use separate env files so you can switch between them without conflict.

6 Build

From the same Windows cmd, in the service folder:

build_deploy_msys2.bat

Expected output (first ~20 lines)

==== set_env (MSYS2) applied ====
  MSYS2_ROOT = C:\msys64\mingw64
  QT_DIR     = C:\msys64\mingw64
==================================
protoc:          C:\msys64\mingw64\bin\protoc.exe
grpc_cpp_plugin: C:\msys64\mingw64\bin\grpc_cpp_plugin.exe

Generating stubs from my_service.proto ...
-- The CXX compiler identification is GNU 15.2.0
-- Check for working CXX compiler: C:/msys64/mingw64/bin/c++.exe - skipped
-- Found OpenSSL: ... 3.6.2
-- Found Protobuf: ... 33.x
-- Configuring done
-- Generating done
...
MSYS2 build complete.  Binaries + runtime DLLs collected in: ...\dist-msys2

Output binaries live in dist-msys2\:

  • my_service.exe — the service
  • my_service_client.exe — console client
  • my_service_gui.exe — Qt Widgets GUI (if enabled)
  • libstdc++-6.dll, libgcc_s_seh-1.dll, libwinpthread-1.dll — MinGW runtime
  • libgrpc*.dll, libprotobuf*.dll, libssl*.dll, ... — dependencies
  • Qt6Core.dll, Qt6Widgets.dll, platforms\qwindows.dll, ... — Qt runtime (if GUI enabled)

The folder is self-contained — copy it to another Windows machine and it runs without MSYS2 installed there.

7 Register MSYS2 MinGW64 as a Qt Creator kit

If you use Qt Creator for day-to-day work, register the MSYS2 toolchain as a kit. You then get one-click build + F5 debug against the same compiler, Qt, gRPC, and Protobuf that build_deploy_msys2.bat uses on the command line — no switching between two worlds.

Open Tools → Options… (Preferences on Linux/macOS) and select Kits in the left pane. Across the top you'll see five tabs: Kits | Qt Versions | Compilers | Debuggers | CMake. Work through the other four tabs first; the Kits tab references everything else.

7a. Compilers tab

Click Add → MinGW → C and fill in:

FieldValue
NameMinGW-w64 MSYS2 (x86_64) C
Compiler pathC:\msys64\mingw64\bin\gcc.exe
ABIleave auto-detect (x86-windows-msys-pe-64bit)

Click Apply, then Add → MinGW → C++:

FieldValue
NameMinGW-w64 MSYS2 (x86_64) C++
Compiler pathC:\msys64\mingw64\bin\g++.exe

7b. Debuggers tab

Click Add:

FieldValue
NameGDB (MSYS2 MinGW64)
PathC:\msys64\mingw64\bin\gdb.exe
Typeauto-detected as GDB

7c. Qt Versions tab

Click Add… and browse to:

C:\msys64\mingw64\bin\qmake6.exe

Qt Creator runs qmake6 -query and auto-fills the fields. Rename it to something recognisable: Qt 6 (MSYS2 MinGW64). If you see a warning triangle, the Qt install is incomplete — re-run the mingw-w64-x86_64-qt6-base line from Step 3.

7d. CMake tab

FieldValue
NameCMake (MSYS2 MinGW64)
PathC:\msys64\mingw64\bin\cmake.exe
Versionshould auto-detect to 3.25+

7e. Kits tab — assemble the kit

Click Add for a blank kit and fill in:

FieldValue
NameMSYS2 MinGW 64-bit
Device typeDesktop
DeviceLocal PC (Default)
Compiler — CMinGW-w64 MSYS2 (x86_64) C
Compiler — C++MinGW-w64 MSYS2 (x86_64) C++
DebuggerGDB (MSYS2 MinGW64)
Qt versionQt 6 (MSYS2 MinGW64)
CMake ToolCMake (MSYS2 MinGW64)
CMake generatorclick Change… and pick Ninja

7f. Environment — click Change… next to Environment

Add these three lines (use the Append/Set action):

PATH=C:\msys64\mingw64\bin;${PATH}
MSYSTEM=MINGW64
CHERE_INVOKING=1
  • PATH makes protoc, DLLs, and windeployqt findable at build and run time.
  • MSYSTEM=MINGW64 tells MSYS-aware helpers (pkg-config, some .sh scripts) which subsystem is active.
  • CHERE_INVOKING keeps MSYS2 bash scripts in the project dir instead of /home/<user>.

7g. CMake Configuration — click Change… next to CMake Configuration

CMAKE_PREFIX_PATH:PATH=%{Qt:QT_INSTALL_PREFIX};C:/msys64/mingw64
CMAKE_BUILD_TYPE:STRING=Release

The semicolon turns CMAKE_PREFIX_PATH into a two-entry CMake list: Qt's own install first (so find_package(Qt6) works), then MSYS2 (so find_package(gRPC|Protobuf|absl) works). Use forward slashes — CMake prefers them on Windows.

Click the star next to the kit name to make it the default.

7h. Verify

Open the project's CMakeLists.txt. When prompted for a kit, tick MSYS2 MinGW 64-bit and click Configure Project. The General Messages pane should include: 

-- The CXX compiler identification is GNU 13.x.x
-- Found Qt6:   ... C:/msys64/mingw64/lib/cmake/Qt6/Qt6Config.cmake
-- Found gRPC: ... C:/msys64/mingw64/lib/cmake/grpc/gRPCConfig.cmake
-- Found Protobuf: ... C:/msys64/mingw64/lib/cmake/protobuf
-- Configuring done
-- Generating done

Ctrl+B builds; F5 launches under gdb.exe with stdout in the Application Output pane and working breakpoints.

Qt Creator kit gotchas

SymptomFix
Red triangle on kit: "No Qt version set" Section 7c didn't save — re-add qmake6.exe and click Apply.
find_package(gRPC) fails inside Qt Creator but works on the command line CMAKE_PREFIX_PATH didn't save, or you deleted the existing %{Qt:QT_INSTALL_PREFIX} entry. Re-edit 7g, keep the semicolon-joined form.
Build succeeds but exe silent-dies when you press Run PATH in 7f wasn't applied. Re-open Environment, confirm the three lines survived a Qt Creator restart.
Clang code model squiggles on <grpcpp/grpcpp.h> even though builds pass Edit → Preferences → C++ → Code Model → enable Add project include paths, then close + reopen the project.
fatal error: 'bits/c++config.h' in the Issues pane Clang code model is pointing at a non-MSYS2 compiler. In the kit, confirm C++ compiler is MinGW-w64 MSYS2 (x86_64) C++.
windeployqt missing when building the GUI target pacman -S mingw-w64-x86_64-qt6-tools — it's separate from qt6-base.

After this, everything build_deploy_msys2.bat does on the command line — compile, link, stub generation via MSYS2 protoc, Qt deployment via windeployqt — works inside Qt Creator with one-click build + F5 debug. Same binaries, same DLLs, no split toolchain.

Troubleshooting

SymptomFix
pacman: command not found You opened plain cmd instead of the MSYS2 terminal. Launch "MSYS2 UCRT64" from Start Menu.
Mirror / SSL errors during Step 3 Re-run the pacman -S command 2–3 times; pacman rotates mirrors. If persistent, temporarily disable VPN or corporate proxy.
signature is unknown trust / signature is invalid Your MSYS2 install is old and its PGP keyring expired. Fix: 
pacman -Sy --needed --noconfirm msys2-keyring
pacman-key --init
pacman-key --populate msys2
pacman -Scc --noconfirm
pacman -Syu --noconfirm
HTTP server doesn't seem to support byte ranges Partial / corrupted cached package. Delete the cache and retry: 
pacman -Scc --noconfirm
ERROR: g++ not found when running build_deploy_msys2.bat Check MSYS2_ROOT in set_env_msys2.bat points at the folder containing bin\g++.exe.
MSYS2 package mingw-w64-x86_64-grpc is not installed Step 3 was skipped or didn't finish. Re-run it from MSYS2 UCRT64.
PROTOBUF_NAMESPACE_OPEN does not name a type Stale stubs from a different toolchain. Fix: 
del proto\my_service.pb.* proto\my_service.grpc.pb.*
rmdir /s /q build-msys2 client\build-msys2
build_deploy_msys2.bat
(The generated script already does this automatically since v2; if you're still seeing the error, your scripts are out-of-date.)
my_service_gui.exe exits silently (no window) Qt runtime wasn't deployed. Re-run build_deploy_msys2.bat; it invokes windeployqt-qt6.exe to copy Qt6*.dll and platforms\qwindows.dll into dist-msys2\.
Error mentions vcpkg even though I'm using MSYS2 You ran build_deploy_mingw.bat (vcpkg-based) or build_deploy.bat (MSVC), not build_deploy_msys2.bat. Check the exact filename.

Uninstall / Reset

If the keyring is hopelessly corrupted and you'd rather start fresh:

:: From Windows cmd (NOT inside MSYS2):
rmdir /s /q C:\msys64
:: Then re-download the installer from msys2.org and repeat Step 1.

A fresh install ships a current keyring, so Steps 2–3 take maybe 15 minutes and avoid all the "key expired" errors.

Disk-space tip

MSYS2's qt6-base + qt6-tools is ~350 MB. If you also have Qt installer's MinGW 11.2 kit and you never plan to use it, free disk space with:

  1. Open Qt Maintenance Tool.
  2. Uncheck Qt 6.x → MinGW 11.2.0 64-bit and Developer and Designer Tools → MinGW 11.2.0 64-bit.
  3. Click Update. Frees ~1 GB.

Keep Qt installer's MSVC kit — build_deploy.bat still uses it.
