Architecture Overview

A MicroserviceBase service is a pure-C++ gRPC server built on top of a small runtime library (microservice_base::runtime) that handles the cross-cutting concerns: Consul registration, health checks, graceful shutdown, and the gRPC boilerplate. Your code only writes:

  • a .proto describing the API,
  • a domain class with the business logic (no gRPC, no Consul),
  • a gRPC adapter translating between the two.

Clients (console or Qt) build against the same .proto and use ServiceClient<T> which resolves the service by name via Consul and creates a gRPC channel. Everything runs under Nomad in production.

The three diagrams below show the static class structure (what to inherit and call), the runtime component layout (who talks to whom), and the end-to-end flow from a GUI button click to the service and back.

End-to-end call flow. The deferred QTimer::singleShot is deliberate: it lets the window paint before the first network call, so the GUI never looks frozen even if Consul is slow.

Hexagonal discipline: domain/ has zero dependencies on gRPC, Qt, or Consul. It is pure C++ — easy to unit-test and reusable beyond this transport.

Environment Setup — set_env

Every scaffold ships with a central set_env.bat (and set_env.sh on POSIX) at the project root. It defines all paths the build scripts need in one place, and is call-ed (or source-d) by build_deploy, generate_stubs, and build_wasm.

:: so CI or System Environment Variables win.

if not defined NINJA_DIR set "NINJA_DIR="

if defined NINJA_DIR if exist "%NINJA_DIR%\ninja.exe" set "PATH=%NINJA_DIR%;%PATH%"

:: MSVC compiler — auto-initialise cl.exe + Windows SDK from a plain cmd.
if not defined VS_DEV_CMD set "VS_DEV_CMD=C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat"
if not defined VSCMD_ARG_TGT_ARCH (
    if exist "%VS_DEV_CMD%" call "%VS_DEV_CMD%" >nul
)

:: Qt install prefix — needed by the Widgets GUI client.
if not defined QT_DIR set "QT_DIR=C:\Qt\6.7.1\msvc2019_64"

set_env.sh (Linux / macOS)

: "${VCPKG_ROOT:=$HOME/vcpkg}"
export VCPKG_ROOT

: "${CMAKE_DIR:=}"
[ -n "$CMAKE_DIR" ] && [ -x "$CMAKE_DIR/cmake" ] && export PATH="$CMAKE_DIR:$PATH"

Edit set_env once for your machine. All other scripts source it, so you never need to duplicate paths across build_deploy.bat, generate_stubs.bat, etc.

1 Define the Proto

Create proto/my_service.proto:

syntax = "proto3";

package myservice.v1;

service MyService {
  rpc Echo   (EchoRequest)   returns (EchoResponse);
  rpc Add    (AddRequest)    returns (AddResponse);
  rpc Stream (StreamRequest) returns (stream Event);
}

message EchoRequest   { string message = 1; }
message EchoResponse  { string result  = 1; }
message AddRequest    { int32  a = 1; int32 b = 2; }
message AddResponse   { int32  result = 1; }
message StreamRequest { int32  count = 1; }
message Event         { int32  sequence = 1; string data = 2; }
The scaffold generator always names the single response field result. If you author the proto by hand, keep that convention so the generated GUI can display the response uniformly.

2 Implement the Domain

src/domain/MyService.h:

#pragma once
#include <cstdint>
#include <string>

class MyService {
public:
    std::string echo(const std::string& message) const;
    int32_t     add(int32_t a, int32_t b)           const;
};

src/domain/MyService.cpp:

#include "MyService.h"

std::string MyService::echo(const std::string& m) const { return "echo: " + m; }
int32_t     MyService::add(int32_t a, int32_t b)  const { return a + b; }
No #include <grpcpp/grpcpp.h> here — that's the rule. The domain class should also be usable by tests, CLIs, or any other transport without touching gRPC.

3 Implement the gRPC Adapter

src/adapters/api/MyGrpcAdapter.h:

#pragma once
#include <grpcpp/grpcpp.h>
#include "my_service.grpc.pb.h"
#include "domain/MyService.h"

class MyGrpcAdapter final : public myservice::v1::MyService::Service {
public:
    explicit MyGrpcAdapter(::MyService& domain) : m_domain(domain) {}

    grpc::Status Echo(grpc::ServerContext*,
        const myservice::v1::EchoRequest*,  myservice::v1::EchoResponse*) override;
    grpc::Status Add(grpc::ServerContext*,
        const myservice::v1::AddRequest*,   myservice::v1::AddResponse*)  override;

private:
    ::MyService& m_domain;
};

src/adapters/api/MyGrpcAdapter.cpp:

#include "MyGrpcAdapter.h"

grpc::Status MyGrpcAdapter::Echo(grpc::ServerContext*,
    const myservice::v1::EchoRequest* req, myservice::v1::EchoResponse* resp) {
    resp->set_result(m_domain.echo(req->message()));
    return grpc::Status::OK;
}

grpc::Status MyGrpcAdapter::Add(grpc::ServerContext*,
    const myservice::v1::AddRequest* req, myservice::v1::AddResponse* resp) {
    resp->set_result(m_domain.add(req->a(), req->b()));
    return grpc::Status::OK;
}

5 Entry Point

src/main.cpp:

#include <iostream>
#include "MicroserviceBase/ServiceRunner.h"
#include "Settings.h"
#include "domain/MyService.h"
#include "adapters/api/MyGrpcAdapter.h"

int main() {
    try {
        Settings settings;
        MyService domain;
        MyGrpcAdapter adapter(domain);

        microservice_base::ServiceRunner runner(settings, {"v1"});
        runner.addService(&adapter, "myservice.v1.MyService");
        runner.serveForever();
    } catch (const std::exception& e) {
        std::cerr << "FATAL: " << e.what() << std::endl;
        return 1;
    }
    return 0;
}
What ServiceRunner::serveForever() does:
1. Starts the gRPC server (dynamic port if grpc_port=0)
2. Enables the gRPC health-check protocol (used by Consul)
3. Enables gRPC reflection (used by the Manager GUI + grpcurl)
4. Registers with Consul — including a gRPC health check
5. Installs signal handlers (SIGINT / SIGTERM; SIGBREAK on Windows)
6. Blocks until a shutdown signal arrives
7. Deregisters from Consul and stops the gRPC server gracefully

6 CMakeLists.txt

The generated CMakeLists.txt prefers pre-generated proto stubs (from proto/) and falls back to auto-generating at build time if they aren't there yet. It also auto-detects vcpkg from VCPKG_ROOT so you can open the project in Qt Creator without passing -DCMAKE_TOOLCHAIN_FILE. 

cmake_minimum_required(VERSION 3.16)
project(my_service VERSION 1.0.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# --- Auto-detect vcpkg from VCPKG_ROOT ---
if(NOT CMAKE_TOOLCHAIN_FILE AND DEFINED ENV{VCPKG_ROOT})
    set(CMAKE_TOOLCHAIN_FILE "$ENV{VCPKG_ROOT}/scripts/buildsystems/vcpkg.cmake"
        CACHE PATH "vcpkg toolchain (auto-detected)")
endif()

find_package(gRPC     CONFIG REQUIRED)
find_package(Protobuf CONFIG REQUIRED)
find_package(CURL     CONFIG REQUIRED)

# MicroserviceBase C++ runtime
add_subdirectory(
    "${CMAKE_CURRENT_SOURCE_DIR}/../../MicroserviceBase/runtime_cpp"
    "${CMAKE_CURRENT_BINARY_DIR}/microservice_base_runtime")

# --- Proto stubs: pre-gen preferred, auto-gen fallback ---
set(PROTO_DIR "${CMAKE_CURRENT_SOURCE_DIR}/proto")
if(EXISTS "${PROTO_DIR}/my_service.pb.h")
    set(MY_SERVICE_SRCS "${PROTO_DIR}/my_service.pb.cc" "${PROTO_DIR}/my_service.grpc.pb.cc")
    set(MY_SERVICE_INC  "${PROTO_DIR}")
else()
    set(GEN_DIR "${CMAKE_CURRENT_BINARY_DIR}/gen")
    file(MAKE_DIRECTORY "${GEN_DIR}")
    get_target_property(_protoc   protobuf::protoc       LOCATION)
    get_target_property(_grpc_cpp gRPC::grpc_cpp_plugin  LOCATION)
    add_custom_command(
        OUTPUT
          "${GEN_DIR}/my_service.pb.cc"      "${GEN_DIR}/my_service.pb.h"
          "${GEN_DIR}/my_service.grpc.pb.cc" "${GEN_DIR}/my_service.grpc.pb.h"
        COMMAND ${_protoc}
          --proto_path="${PROTO_DIR}"
          --cpp_out="${GEN_DIR}" --grpc_out="${GEN_DIR}"
          --plugin=protoc-gen-grpc="${_grpc_cpp}"
          "${PROTO_DIR}/my_service.proto"
        DEPENDS "${PROTO_DIR}/my_service.proto")
    set(MY_SERVICE_SRCS "${GEN_DIR}/my_service.pb.cc" "${GEN_DIR}/my_service.grpc.pb.cc")
    set(MY_SERVICE_INC  "${GEN_DIR}")
endif()

add_executable(my_service
    src/main.cpp
    src/domain/MyService.cpp
    src/adapters/api/MyGrpcAdapter.cpp
    ${MY_SERVICE_SRCS})

target_include_directories(my_service PRIVATE src ${MY_SERVICE_INC})

target_link_libraries(my_service PRIVATE
    microservice_base::runtime
    gRPC::grpc++ gRPC::grpc++_reflection
    protobuf::libprotobuf)

7 Proto Stubs — Generate Once, Share with the Client

The generate_stubs script lives in proto/, not in client/, because both the service and the client consume the same stubs. Running it once produces: 

proto/
├── my_service.proto
├── my_service.pb.h / .pb.cc         # protobuf message classes
└── my_service.grpc.pb.h / .grpc.pb.cc # gRPC Stub + Service base
Windows
cd my_service\proto

Linux

What the two .h files give you

FileContentsWho uses it
my_service.pb.h Protobuf message classes (EchoRequest, EchoResponse, …) with setters, getters, and serialization. No networking. Both service and client
my_service.grpc.pb.h MyService::Service (abstract base you inherit in the server adapter) and MyService::Stub (concrete client handle). gRPC channel handling. Service adapter & client
The stubs pulled from proto/ are the same binary compatible set used by both the service and the client — this avoids subtle ABI mismatches if you regenerate one side and not the other.

8 Console Client — ServiceClient<T>

The client subproject at client/ builds a console binary my_service_client.exe that uses the runtime's ServiceClient<T> template. It resolves the service by name through Consul and creates a gRPC channel for you. 

#include <iostream>
#include <grpcpp/grpcpp.h>
#include "my_service.grpc.pb.h"
#include "MicroserviceBase/ServiceClient.h"

int main(int argc, char* argv[]) {
    // Consul lookup (recommended):
    //   my_service_client my_service
    microservice_base::ServiceClient<myservice::v1::MyService>
        client("my_service");
    std::cout << "Connected to " << client.target() << std::endl;

    grpc::ClientContext ctx;
    myservice::v1::EchoRequest  req;
    req.set_message("hello");
    myservice::v1::EchoResponse resp;
    auto status = client.stub().Echo(&ctx, req, &resp);

    if (status.ok()) std::cout << "Reply: " << resp.result() << std::endl;
    else std::cerr << "Error: " << status.error_message() << std::endl;
    return 0;
}

Both a Consul-based constructor and a direct one are available: 

// Consul-based (uses CONSUL_ADDR env var or http://127.0.0.1:8500)
ServiceClient<MyService> c1("my_service");

// Direct host:port (bypass Consul — useful for debugging)
ServiceClient<MyService> c2("my_service", "127.0.0.1:50051", true);

The MethodBinding pattern

Each method is represented by a struct captured in a std::vector. rebuildForm(idx) reads the binding's params to lay out widgets; onSend() calls the binding's invoke lambda, which casts the widgets back and runs the correct RPC. 

struct ParamSpec { QString name; QString type; };
struct MethodBinding {
    QString name;
    std::vector<ParamSpec> params;
    std::function<QString(const std::vector<QWidget*>&)> invoke;
};

// Example binding generated for Add(int32 a, int32 b) → int32
MethodBinding b;
b.name = "Add";
b.params = { {"a", "int32"}, {"b", "int32"} };
b.invoke = [this](const std::vector<QWidget*>& ws) -> QString {
    grpc::ClientContext ctx;
    myservice::v1::AddRequest req;
    req.set_a(qobject_cast<QSpinBox*>(ws[0])->value());
    req.set_b(qobject_cast<QSpinBox*>(ws[1])->value());
    myservice::v1::AddResponse resp;
    auto st = m_client->stub().Add(&ctx, req, &resp);
    if (!st.ok()) return "[error] " + QString::fromStdString(st.error_message());
    return QString::number(resp.result());
};
m_methods.push_back(std::move(b));
Why defer the Consul lookup with QTimer::singleShot(0, …)?
Calling ServiceClient in the constructor blocks on a network round-trip. Deferring it until after app.exec() starts lets the window paint first — so even with a slow or unreachable Consul the GUI never looks frozen.

10 build_deploy — One Command to Rule Them All

build_deploy.bat / .sh is the recommended build entry point. It runs every step end-to-end:

  1. Source set_env (vcpkg, CMake, MSVC, Qt paths)
  2. If proto/ has no .pb.h, call generate_stubs
  3. Configure + build the service (build/)
  4. Configure + build the client + GUI (client/build/)
  5. Copy all *.exe and *.dll from both build trees into dist/
  6. Run windeployqt on the GUI binary so Qt DLLs + platforms/qwindows.dll land in dist/

Usage

Windows
cd my_service
build_deploy.bat

:: Output — a ready-to-ship folder:
:: dist\my_service.exe
:: dist\my_service_client.exe
:: dist\my_service_gui.exe       (+ Qt6*.dll, platforms\, styles\, …)
:: dist\*.dll                     (grpc, protobuf, abseil, openssl, …)
Linux
cd my_service
./build_deploy.sh
Windows quirk: copying just the .exe into another folder typically fails silently — the loader can't find abseil_dll.dll, libprotobuf.dll, etc. that vcpkg deployed next to build\Release\. build_deploy.bat mirrors the whole set into dist/ so the binaries are self-contained.

10b MinGW Variant — build_deploy_mingw.bat

Every C++ scaffold now ships a second Windows deploy script, build_deploy_mingw.bat, for users who prefer MinGW (g++ + Ninja) over MSVC (cl.exe + MSBuild). It builds into build-mingw\ / client\build-mingw\ and deploys into dist-mingw\ — so you can keep an MSVC and a MinGW build side-by-side without them colliding.

Prerequisites for the MinGW path

  1. Install the Qt MinGW 11.2.0 64-bit kit via Qt Maintenance Tool (Tools → MinGW 11.2.0 64-bit, plus the matching Qt 6.x MinGW kit).
  2. Install Ninja (bundled: C:\Qt\Tools\Ninja).
  3. Tell vcpkg to build MinGW-compatible binaries: 
    set VCPKG_DEFAULT_TRIPLET=x64-mingw-dynamic
%VCPKG_ROOT%\vcpkg install grpc:x64-mingw-dynamic ^
                           protobuf:x64-mingw-dynamic ^
                           curl:x64-mingw-dynamic
    First-time compile of these ports takes 20–60 min.

Edit the three paths at the top if yours differ

if not defined MINGW_DIR     set "MINGW_DIR=C:\Qt\Tools\mingw1120_64\bin"
if not defined NINJA_DIR     set "NINJA_DIR=C:\Qt\Tools\Ninja"
if not defined QT_DIR        set "QT_DIR=C:\Qt\6.7.1\mingw_64"
if not defined VCPKG_TRIPLET set "VCPKG_TRIPLET=x64-mingw-dynamic"

ABI reminder: MinGW binaries cannot link against MSVC-built DLLs (including a vcpkg tree configured for x64-windows). If you switch toolchains, either keep separate vcpkg trees per triplet or rely on vcpkg's automatic per-triplet installed/ subfolders (which is what this script uses via -DVCPKG_TARGET_TRIPLET).
When to pick MinGW: no Visual Studio install, or you already have a MinGW toolchain you trust.
When to stay on MSVC: you're consuming prebuilt third-party MSVC libraries, faster first-time vcpkg install (most ports ship binaries for x64-windows), or you want to debug with Visual Studio.

12 Qt Creator Setup

Qt Creator does not run set_env.bat, so the vcpkg toolchain isn't picked up by default. Pick one of the three fixes below — the second is the least intrusive.

A. Permanent: set VCPKG_ROOT as a System Environment Variable

  1. Open Windows → "Edit environment variables for your account".
  2. Add VCPKG_ROOT = C:\vcpkg (or wherever you cloned it).
  3. Restart Qt Creator — the scaffold's CMakeLists auto-detects it.

B. Per-project: tell Qt Creator the toolchain file

  1. Open the project in Qt Creator.
  2. Projects (left pane) → Build → Initial Configuration → Add.
  3. Key: CMAKE_TOOLCHAIN_FILE, Value: C:/vcpkg/scripts/buildsystems/vcpkg.cmake.
  4. Click Run CMake.

C. For Qt Widgets GUI — also set QT_DIR

When the GUI client references find_package(Qt6), Qt Creator already passes its own Qt via CMAKE_PREFIX_PATH. If you build from the command line instead, make sure QT_DIR in set_env.bat points at the right kit (e.g. C:\Qt\6.7.1\msvc2019_64).

AUTOUIC / "ui_MainWindow.h not found" errors in Qt Creator's editor are normal before the first build. The file is generated by CMake into the build tree and only picked up by the code model after you hit Build once. After that, Tools → C++ → Reset Code Model clears the squiggles.

13 Deploy with Nomad (Optional)

job "my_service" {
  datacenters = ["dc1"]
  type        = "service"

  group "default" {
    count = 1
    network { port "grpc" {} }

    task "server" {
      driver = "raw_exec"

      config {
        command = "/path/to/my_service"          # Linux
        # command = "C:/path/to/my_service.exe"  # Windows
      }

      env {
        MY_SERVICE_GRPC_PORT      = "${NOMAD_PORT_grpc}"
        MY_SERVICE_ADVERTISE_ADDR = "127.0.0.1"
        MY_SERVICE_CONSUL_ADDR    = "http://127.0.0.1:8500"
      }

      resources { cpu = 100 ; memory = 128 }
    }
  }
}

Submit via the Manager GUI: Service Network → Nomad → Submit Job, or from the CLI: nomad job run my_service.nomad.hcl.
