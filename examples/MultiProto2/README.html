Full step-by-step: load both projects in Qt Creator with the Desktop Qt 6.x MinGW 64-bit kit, no rebuild

The fastest path that loads both the server (this project) and the qt_client_grpcpp/ client into Qt Creator with the Desktop Qt 6.x MinGW 64-bit kit (no preset, no full vcpkg compile). Follow exactly — each step prevents a common pitfall covered in the troubleshooting section.

One-time setup

  1. Set system env vars (in a regular CMD, replace the paths with yours if different): 
    setx VCPKG_ROOT C:\vcpkg
setx QT_DIR C:\Qt\6.11.0\mingw_64
setx QT_MINGW_BIN C:\Qt\Tools\mingw1310_64\bin
    setx writes the registry — only future processes see the change.
  2. Fully close Qt Creator. Check Task Manager for stray qtcreator.exe and kill them. Otherwise the running Qt Creator keeps the old (empty) env, and the autodetect block in CMakeLists won’t see VCPKG_ROOT.
  3. Download the prebuilt zip from the SharePoint link below (in the Use prebuilt libraries section) and save anywhere, e.g. C:\prebuilt\vcpkg_installed_x64-mingw-qt.zip.

Step 1 — configure the server (this) project

  1. Open Qt Creator. File → Open File or Project → pick this project’s CMakeLists.txt.
  2. Configure dialog: untick every preset. Tick only the kit Desktop Qt 6.x MinGW 64-bit. Click Configure Project.
  3. The first configure may try to install vcpkg packages or fail at find_package(gRPC) — that’s fine; we just need the build dir to exist. If a long vcpkg compile starts: Build → Cancel Build immediately.
  4. Build → Clear CMake Configuration. This wipes CMakeCache.txt so the vars you’re about to add actually take effect. (Clean alone does NOT clear cache.)
  5. Projects (Ctrl+5) → Build (under Desktop Qt 6.x MinGW 64-bit) → Initial Configuration → Add. Add these five entries (replace placeholders with your vcpkg checkout and project absolute paths; leave forward slashes and the var-name S as written):
    Add asNameValue
    String CMAKE_TOOLCHAIN_FILE C:/vcpkg/scripts/buildsystems/vcpkg.cmake
    String VCPKG_TARGET_TRIPLET x64-mingw-qt
    String VCPKG_OVERLAY_TRIPLETS C:/path/to/your/project/triplets
    String VCPKG_OVERLAY_PORTS C:/path/to/your/project/ports
    Boolean VCPKG_MANIFEST_INSTALL OFF
    Pitfall reminders:
    • Var name is plural: VCPKG_OVERLAY_TRIPLETS (with S).
    • Use absolute paths for overlay vars. Qt Creator does not expand ${sourceDir} in Initial Configuration.
    • Forward slashes / only.
    • VCPKG_MANIFEST_INSTALL=OFF is what tells the vcpkg toolchain to skip its 30–60 min compile. Without this, vcpkg overwrites the prebuilt tree you’re about to import.
  6. Build → Run CMake. This will fail at find_package(gRPC) — expected: the build dir build\Desktop_Qt_*\ is now created but vcpkg_installed/ isn’t populated yet.

Step 2 — configure the qt_client_grpcpp project

  1. File → Open File or Project → qt_client_grpcpp\CMakeLists.txt (it’s a separate sub-project with its own build dir).
  2. Configure dialog: untick every preset. Tick only Desktop Qt 6.x MinGW 64-bit. Click Configure Project. Same as step 1: cancel any vcpkg compile, then Clear CMake Configuration.
  3. Projects (Ctrl+5) → Build → Initial Configuration → Add. Same five entries as the server, but the two overlay paths point at the parent triplets/ and ports/ (one level up from qt_client_grpcpp/):
    Add asNameValue
    String CMAKE_TOOLCHAIN_FILE C:/vcpkg/scripts/buildsystems/vcpkg.cmake
    String VCPKG_TARGET_TRIPLET x64-mingw-qt
    String VCPKG_OVERLAY_TRIPLETS C:/path/to/your/project/triplets
    String VCPKG_OVERLAY_PORTS C:/path/to/your/project/ports
    Boolean VCPKG_MANIFEST_INSTALL OFF
  4. Build → Run CMake. Will fail at find_package(Protobuf) — expected; the qt_client_grpcpp\build\Desktop_Qt_*\ dir is now created.

Step 3 — populate vcpkg_installed/ from the prebuilt zip

  1. Open a regular CMD/PowerShell. cd to the parent project (this directory).
  2. Run import once — it auto-detects every build dir (server and qt_client_grpcpp) and extracts the zip into all of them: 
    import_prebuilt.bat C:\prebuilt\vcpkg_installed_x64-mingw-qt.zip
  3. Verify both build dirs got the tree: 
    dir build\Desktop_Qt_*\vcpkg_installed\x64-mingw-qt\share\grpc\
dir qt_client_grpcpp\build\Desktop_Qt_*\vcpkg_installed\x64-mingw-qt\share\grpc\
    Both should list gRPCConfig.cmake. If only one is present, your other project’s build dir wasn’t created yet — go back to whichever step you skipped.

Step 4 — re-run CMake on both projects

  1. In Qt Creator, switch to the server project (top-left project selector) → Build → Run CMake. Should complete in ~1–3 sec. In General Messages: 
    -- Found gRPC: <build-dir>/vcpkg_installed/x64-mingw-qt/share/grpc
-- Found Protobuf: ...
-- Configuring done
  2. Switch to the qt_client_grpcpp project → Build → Run CMake. Same ~1–3 sec result.
  3. Build → Build All on both projects. Project code compiles in ~30 sec – 2 min; vcpkg deps are not rebuilt.

Sanity check: did it really skip the rebuild?

In General Messages you should not see:

-- Building boringssl[core]:x64-mingw-qt...
-- Building abseil[core]:x64-mingw-qt...
-- Building grpc:x64-mingw-qt...

If you do, VCPKG_MANIFEST_INSTALL=OFF didn’t reach the toolchain. Check that:

  • The Initial Configuration entry is type Boolean (or String OFF) — not deleted.
  • You ran Clear CMake Configuration after adding it (cached configures don’t pick up new -D flags).

If you forgot one of the four toolchain vars or used a wrong path, the failure surfaces as Could not find a package configuration file provided by "gRPC" at find_package — not as a build of grpc itself.

Environment setup (one-time)

The vcpkg path needs three environment variables. Set them once system-wide via setx — then close every open terminal/Qt Creator and start a fresh one so the new values are inherited (setx only affects new processes).

1. VCPKG_ROOT — vcpkg checkout

If you don’t have vcpkg installed yet:

git clone https://github.com/microsoft/vcpkg.git C:\vcpkg
C:\vcpkg\bootstrap-vcpkg.bat

Then point VCPKG_ROOT at it:

setx VCPKG_ROOT C:\vcpkg

(Replace C:\vcpkg with wherever you cloned it, e.g. D:\Project\Out\vcpkg.)

2. QT_DIR — Qt MinGW prefix

Path to the directory containing lib\cmake\Qt6\:

setx QT_DIR C:\Qt\6.11.0\mingw_64

(Adjust the version number to your actual Qt install.)

3. QT_MINGW_BIN — Qt MinGW compiler bin

Path to the directory containing g++.exe:

setx QT_MINGW_BIN C:\Qt\Tools\mingw1310_64\bin

Verify

Open a new terminal and run:

echo %VCPKG_ROOT%
echo %QT_DIR%
echo %QT_MINGW_BIN%
dir %VCPKG_ROOT%\vcpkg.exe
dir %QT_DIR%\bin\Qt6Core.dll
dir %QT_MINGW_BIN%\g++.exe

All three dir commands should print a file entry. If any errors with File Not Found, double-check the path and re-run setx.

For Qt Creator specifically

If Qt Creator was already running when you set these vars, it won’t see the new values until restarted. Either:

  • Close + restart Qt Creator (simplest), or
  • Set them per-project at Projects → Build → Build Environment (Add → type the var + value).

How vcpkg + Qt MinGW works

Both server and client need Google’s grpc++ and protobuf C++ libraries. We compile them from source via vcpkg using the Qt-installer’s MinGW 13.1.0 compiler so every binary in the project shares one libstdc++ ABI. Mixing toolchains (e.g. MSYS2 grpc + Qt MinGW client) yields cryptic link errors and silent crashes at std::string boundaries.

The pieces that make this work:

  1. triplets/x64-mingw-qt.cmake — custom vcpkg triplet. Pins VCPKG_TARGET_ARCHITECTURE=x64, dynamic CRT/library linkage, and chainloads qt-mingw-toolchain.cmake which sets CMAKE_C_COMPILER and CMAKE_CXX_COMPILER to absolute paths inside C:\Qt\Tools\mingw1310_64\bin\. Vcpkg uses Qt’s gcc to build every port regardless of what’s on PATH.
  2. ports/grpc/00018-gcc13-per-cpu-ice-workaround.patch — gcc 13.1.0 has an internal compiler error on grpc 1.76’s per_cpu.h NSDMI brace-init. The patch moves the std::unique_ptr<T[]> allocation into the constructor body, sidestepping the ICE. An overlay-port applies it on top of vcpkg’s stock grpc port.
  3. Host tools (cross-triplet codegen) — vcpkg builds protoc and grpc_cpp_plugin for the host triplet (x64-windows) and uses them at build time to generate .pb.h/.pb.cc stubs. Our CMakeLists pre-sets Protobuf_PROTOC_EXECUTABLE at build/.../vcpkg_installed/x64-mingw-qt/tools/protobuf/protoc.exe so it doesn’t require x64-windows/tools/protobuf/. grpc_cpp_plugin still ships from x64-windows/tools/grpc/ because vcpkg’s grpc port doesn’t build it for the target triplet.
  4. Server reflection — the overlay-port forces gRPC_BUILD_CODEGEN=ON in portfile.cmake, which causes upstream grpc to build and install libgrpc++_reflection.a + register the gRPC::grpc++_reflection CMake target. Without that override, vcpkg’s manifest-mode feature selection drops codegen for the target triplet (it stays on for the host triplet only) and upstream’s add_library(grpc++_reflection ...) block gets skipped — the Manager GUI then sees UNIMPLEMENTED from every reflection RPC. CMakeLists keeps an if(TARGET gRPC::grpc++_reflection) guard for unusual grpc distributions; the bridge also has a LocalProtoClient fallback that compiles .proto files from disk if reflection is somehow still missing.
  5. vcpkg.json declares grpc + protobuf + curl (Consul HTTP), with features: ["codegen"] for grpc so protoc-gen-grpc is available. Manifest names are hyphenated (multi-proto2-server-vcpkg); underscores are reserved.

First build cost: vcpkg compiles boringssl, abseil, c-ares, re2, zlib, openssl, protobuf, grpc, curl — about 30–60 min on a typical workstation, mostly idle. Subsequent builds in the same triplet hit the binary cache at %LOCALAPPDATA%\vcpkg\archives\ and complete in seconds.

Build & run in Qt Creator

Recommended: use the bundled CMake preset

  1. Open CMakeLists.txt in Qt Creator. Qt Creator detects the bundled CMakePresets.json and offers two presets:
    • vcpkg-x64-mingw-qt — full vcpkg build (~30–60 min first time).
    • vcpkg-x64-mingw-qt-prebuilt — skip vcpkg install (populate build/.../vcpkg_installed/x64-mingw-qt/ first via import_prebuilt.bat).
  2. Tick the preset(s) you want and click Configure Project. Presets already include CMAKE_TOOLCHAIN_FILE, VCPKG_TARGET_TRIPLET, and overlay paths — no manual wiring required.

Alternative: kit-based flow (Desktop Qt 6.x MinGW 64-bit)

If you prefer to use a Qt kit instead of the preset, you must give Qt Creator the vcpkg toolchain explicitly — it does not auto-detect vcpkg from VCPKG_ROOT the way the CLI build script does.

  1. Set system env vars (one-time): 
    setx VCPKG_ROOT C:\vcpkg
setx QT_DIR C:\Qt\6.11.0\mingw_64
setx QT_MINGW_BIN C:\Qt\Tools\mingw1310_64\bin
    Then fully close Qt Creator and reopen it — setx only writes to the registry; the env vars only reach processes started after the change. An already-running Qt Creator keeps the old (empty) environment.
  2. Open the project → pick the kit Desktop Qt 6.x MinGW 64-bit. In the Initial Configuration panel, click Add → String and add these four entries (replace the project path with yours): 
    CMAKE_TOOLCHAIN_FILE   = C:/vcpkg/scripts/buildsystems/vcpkg.cmake
VCPKG_TARGET_TRIPLET   = x64-mingw-qt
VCPKG_OVERLAY_TRIPLETS = C:/path/to/your/project/triplets
VCPKG_OVERLAY_PORTS    = C:/path/to/your/project/ports
    • Use forward slashes /, not back slashes \ (CMake interprets \Q as an escape).
    • Use absolute paths for the overlay vars. Qt Creator’s Initial Configuration does not expand ${sourceDir} — that’s a CMakePresets-only macro. If you paste ${sourceDir}/triplets, cmake gets it as a literal string, vcpkg can’t find the x64-mingw-qt triplet, and manifest install fails before grpc/protobuf even start to compile.
    • Make sure the var name is plural — VCPKG_OVERLAY_TRIPLETS (with S), not VCPKG_OVERLAY_TRIPLET. vcpkg silently ignores the singular form.
  3. Click Configure Project. First configure: ~30–60 min while vcpkg compiles boringssl + abseil + protobuf + grpc + curl. Subsequent configures: ~1–3 sec (cache hit).
  4. If you've already configured once and it failed: Build → Clear CMake Configuration, then re-add the four Initial Configuration entries above and re-run Run CMake. Once CMakeCache.txt exists in the build dir, subsequent CMake runs do not re-pass -D flags — you must clear it to inject new vars.

Running the GUI from Qt Creator (F5) without copying DLLs

The build links the .exe against vcpkg DLLs in build/<cfg>/vcpkg_installed/x64-mingw-qt/bin/, plus Qt and MinGW runtime DLLs. Windows’ DLL search only looks at the .exe’s folder and %PATH%, so a fresh build run via F5 fails with libprotobuf.dll not found (or Qt6Core.dll, libgcc_s_seh-1.dll, etc.).

Fix once per kit/preset: Projects (Ctrl+5) → Run → Environment → Details → select Path and click Edit. Prepend (semicolon-separated) the three dirs below. Use absolute paths; replace <build-dir> with this project’s build dir shown in the Build tab (e.g. build/Desktop_Qt_*-Debug or build-qt-vcpkg for the preset): 

<build-dir>\vcpkg_installed\x64-mingw-qt\bin;C:\Qt\6.x.y\mingw_64\bin;C:\Qt\Tools\mingw1310_64\bin

For qt_client_grpcpp/ (a separate sub-project with its own build dir), repeat the same edit on its Run → Environment — substituting its build dir. Re-doing this is only required when you change the build dir name (switch between Debug/Release, change kit, etc.); it survives rebuilds.

Permanent alternative: run deploy_qt_vcpkg.bat (server) or cd qt_client_grpcpp && deploy_qt.bat. Each script copies every DLL next to the .exe in dist-qt-vcpkg/; that folder is fully self-contained and runs without any PATH setup. Useful when shipping a build to a teammate or to a test machine.

If you do, VCPKG_MANIFEST_INSTALL=OFF didn’t reach the toolchain — check Initial Configuration still has the entry, then Clear CMake Configuration + Run CMake again.

Where the zip lands: import_prebuilt.bat extracts into every detected build dir’s vcpkg_installed/ subfolder. Each gets its own copy (~184 MB unpacked) so the server, console+widget client, and qt_client_grpcpp can all build independently against the same artifacts.

Sharing your own prebuilt back: after a successful local build, run export_prebuilt.bat to pack build-qt-vcpkg/vcpkg_installed/x64-mingw-qt/ + x64-windows/tools/grpc/ into prebuilt/vcpkg_installed_x64-mingw-qt.zip. Upload to the shared SharePoint folder so other devs save the rebuild cost.

Run sequence (Consul + Nomad)

1. Start the agents (one-time per dev session)

Open two terminals and leave them running.

Terminal A — Consul:

consul agent -dev -client=0.0.0.0 -ui

UI at http://127.0.0.1:8500. Sanity check: consul members — should list one alive member.

Terminal B — Nomad:

Windows needs raw_exec driver enabled. Create C:\nomad\dev.hcl once with:

plugin "raw_exec" {
  config {
    enabled = true
  }
}

Then start the agent:

nomad agent -dev -config=C:\nomad\dev.hcl

UI at http://127.0.0.1:4646. Sanity check: nomad node status.

2. One-time setup: resolve absolute paths in HCL files

Generated deploy\*.nomad.hcl files use a C:/path/to/<project> placeholder. Run this script once after scaffold (or after moving the project folder):

prep_nomad_paths.bat

This rewrites every .hcl file to point at the current project’s absolute path. Idempotent.

3. Submit each service to Nomad

Pick the dist folder matching your build path:

  • MSYS2 build: HCL points at dist-msys2\run_<service>.bat
  • vcpkg build (after deploy_qt_vcpkg.bat): the dist-qt-vcpkg\ copy of the HCL points at dist-qt-vcpkg\run_<service>.bat instead. Submit those from dist-qt-vcpkg\deploy\.

Submit each job:

ServiceSubmitStop
ComSetupDeviceService
nomad job run deploy\com_setup_device_service.nomad.hcl
nomad job stop com_setup_device_service
PowerSupplyService
nomad job run deploy\power_supply_service.nomad.hcl
nomad job stop power_supply_service

After submission, Nomad picks a random free port (defined as port "grpc" { } in the HCL) and exports it as ${NOMAD_PORT_grpc} → the service reads it from <PREFIX>_GRPC_PORT env var and registers in Consul under that port.

4. Verify each service is up

nomad job status <service>
consul catalog services
curl http://127.0.0.1:8500/v1/health/service/<service>?passing=true

The Consul query returns the resolved host:port the UI client uses when Use Consul is checked.

5. Tail logs / stop / restart

nomad alloc logs <alloc-id>        :: stream stdout/stderr
nomad job stop <service>            :: deregister + kill
nomad job run deploy\<service>.nomad.hcl  :: re-submit

Get the alloc ID from nomad job status <service>.

Direct launch (skip Nomad)

Useful for quick smoke tests — the service still registers with Consul if CONSUL_ADDR is reachable:

set <PREFIX>_GRPC_PORT=50051
dist-qt-vcpkg\run_<service>.bat

(Replace <PREFIX> with the env prefix listed in the “Project at a glance” table.)

Common issues & fixes

Click each entry to expand.

Qt Creator: Could not find a package configuration file provided by "gRPC"

Symptom (kit-based flow, build/Desktop_Qt_*-Debug/):

CMake Error at CMakeLists.txt:60 (find_package):
  Could not find a package configuration file provided by "gRPC" ...
  Add the installation prefix of "gRPC" to CMAKE_PREFIX_PATH ...

The cmake invocation has no -DCMAKE_TOOLCHAIN_FILE=... flag, so vcpkg never loads, and the manifest install never runs. Two fixes:

Fix A (recommended): switch to the preset. Close the project, reopen via File → Open File or Project → CMakeLists.txt and select the vcpkg-x64-mingw-qt preset on the import dialog.

Fix B: stay on the kit, but inject toolchain vars manually.

  1. Build → Clear CMake Configuration (Clean alone does NOT clear cache).
  2. Projects (Ctrl+5) → Build → Initial Configuration → Add → String and add all four (replace placeholders with your vcpkg checkout and project absolute paths):
    CMAKE_TOOLCHAIN_FILE   = C:/vcpkg/scripts/buildsystems/vcpkg.cmake
VCPKG_TARGET_TRIPLET   = x64-mingw-qt
VCPKG_OVERLAY_TRIPLETS = C:/path/to/your/project/triplets
VCPKG_OVERLAY_PORTS    = C:/path/to/your/project/ports
    Pitfalls:
    • Use absolute paths for overlay vars — Qt Creator does not expand ${sourceDir} in Initial Configuration (CMakePresets-only macro). Literal ${sourceDir}/triplets reaches vcpkg, which can’t find x64-mingw-qt.cmake and aborts manifest install.
    • Var name is plural: VCPKG_OVERLAY_TRIPLETS (with S). Singular VCPKG_OVERLAY_TRIPLET is silently ignored.
    • Forward slashes only. \ triggers Invalid character escape \Q.
  3. Click Run CMake.

Why the autodetect in CMakeLists.txt didn’t fire: it reads $ENV{VCPKG_ROOT}. If you ran setx VCPKG_ROOT after Qt Creator was launched, the var isn’t in its environment — the warning prints, but the toolchain stays unset and find_package(gRPC) fails.

vcpkg BUILD_FAILED on grpc with gcc 13 ICE

The overlay-port at ports/grpc/ includes patch 00018-gcc13-per-cpu-ice-workaround.patch. If it didn’t apply, delete ports/grpc/portfile.cmake and re-run init_vcpkg_overlay.bat.

Could NOT find Protobuf (missing: Protobuf_PROTOC_EXECUTABLE)

CMakeLists pre-sets Protobuf_PROTOC_EXECUTABLE to build/.../vcpkg_installed/x64-mingw-qt/tools/protobuf/protoc.exe. If your zip doesn’t have host tools, run export_prebuilt.bat from a fully-built dir to pack x64-windows/tools/grpc/ too.

Linker error -ignore:4221 unrecognized

find_package picked vcpkg’s MSVC x64-windows libs instead of our MinGW x64-mingw-qt. Wipe the build dir (rmdir /s /q build\Desktop_Qt_*) and re-configure.

Could not find _grpc_cpp using ... grpc_cpp_plugin.exe

Host tools missing. Copy x64-windows/tools/grpc/ from a complete vcpkg_installed tree, or re-import a zip exported with the latest export_prebuilt.bat (it now packs host plugin).

CMake error Invalid character escape \Q

Stale CMakeFiles\<ver>\CMakeCXXCompiler.cmake from earlier failed configure. Wipe the build dir entirely (Qt Creator Clean is not enough) and Run CMake.

Qt Creator: vcpkg executable not found

Just a warning - the bundled QT_CREATOR_SKIP_VCPKG_SETUP=ON silences it. If you still see it, ensure CMakeLists ran past project().

ninja: manifest \'build.ninja\' still dirty after 100 tries

Code-gen output landing in source tree. Generated files use ${CMAKE_BINARY_DIR}/grpc_gen by design - never change to source dir.

F5 in Qt Creator: libprotobuf.dll / Qt6Core.dll / libgcc_s_seh-1.dll not found

Build dir holds only the .exe + import libs; the actual DLLs live in build/<cfg>/vcpkg_installed/x64-mingw-qt/bin/ (vcpkg deps), C:\Qt\6.x.y\mingw_64\bin\ (Qt), and C:\Qt\Tools\mingw1310_64\bin\ (MinGW runtime). Windows can’t find them on F5. Fix: Projects (Ctrl+5) → Run → Environment → Details → Path → Edit, prepend all three dirs (semicolon-separated). See the “Running the GUI from Qt Creator (F5)” subsection for the full path string. Or just run deploy_qt.bat / deploy_qt_vcpkg.bat — those copy every DLL next to the .exe in dist-qt-vcpkg/, no PATH hack needed.

GUI exe fails at startup with missing Qt DLL (deployed dist)

Re-run the appropriate deploy script. windeployqt auto-detects Debug vs Release from PE header; if it copied wrong variant, delete dist-* and re-run deploy.

Service starts but doesn’t register in Consul

Check CONSUL_ADDR env var (default http://127.0.0.1:8500). In Nomad, set it via env { ... } in the .hcl, or set system-wide before running build_deploy_*.bat.

Service binds wrong port

Each service reads <PREFIX>_GRPC_PORT (e.g. COM_SETUP_DEVICE_SERVICE_GRPC_PORT). Nomad sets it from ${NOMAD_PORT_grpc}; for direct launch, export the env var manually.

Qt Creator: The ABI of the selected debugger does not match the toolchain ABI

CMakePresets can pin compiler paths but has no field for a debugger. Qt Creator’s auto-imported preset kit pairs the MinGW compiler with whatever debugger it auto-detects (often MSVC cdb.exe or a system gdb with a different ABI), hence the warning.

One-time fix (per machine, not per project):

  1. Edit → Preferences → Kits → Debuggers — verify there’s an entry for C:\Qt\Tools\mingw1310_64\bin\gdb.exe. If not: Add → Path = that path, Name = MinGW gdb (Qt 6.11). Apply.
  2. Kits tab → select the auto-imported kit named after the preset (e.g. vcpkg + Qt MinGW 13.1.0 (Release)) → set Debugger to the entry from step 1. Apply + OK.

The fix sticks across project re-imports because Qt Creator stores it in the kit, not the preset. If Qt’s installer already registered the bundled gdb (sometimes as MinGW Debugger), step 1 is unnecessary — pick the existing entry in step 2.
