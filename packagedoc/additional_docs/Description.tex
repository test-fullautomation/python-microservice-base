\section{Description}

\subsection{Overview}

MicroserviceBase is a Python framework for building microservices that communicate through RabbitMQ,
with a built-in GUI for monitoring, a local process hub for lifecycle management, and a service
registry for dynamic discovery. The system follows hexagonal architecture principles,
ensuring testability, maintainability, and extensibility.

\begin{figure}[!htb]
\centering
\includegraphics[width=0.95\textwidth]{pictures/overview.png}
\caption{MicroserviceBase System Overview}
\label{fig:overview}
\end{figure}

\subsubsection{Key Features}

\begin{itemize}
   \item \textbf{Microservice Framework}: Base classes for creating services with RPC and pub/sub patterns
   \item \textbf{Service Registry}: Dynamic service registration and discovery via RabbitMQ exchange
   \item \textbf{FastAPI Bridge}: REST API and WebSocket gateway connecting GUI to microservices
   \item \textbf{Manager GUI}: Electron + browser-based dashboard for monitoring and controlling services
   \item \textbf{Local Process Hub}: Start, stop, and manage service processes with graceful shutdown
   \item \textbf{Multi-Broker Support}: Connect to multiple RabbitMQ brokers simultaneously
   \item \textbf{Service Import}: Import microservice packages (folder or zip) into the local hub
   \item \textbf{Service Creator}: Interactive wizard for scaffolding new microservices
   \item \textbf{Standalone Installer}: Package as Windows desktop application (DevAtServGUI)
\end{itemize}

\subsubsection{Design Philosophy}

MicroserviceBase follows several key design principles:

\begin{enumerate}
   \item \textbf{Hexagonal Architecture}: Domain logic is isolated from external concerns via ports and adapters
   \item \textbf{Factory Pattern}: All components are created through factories, enabling easy swapping
   \item \textbf{Dual Hosting}: GUI works in both Electron (desktop) and browser modes
   \item \textbf{Graceful Shutdown}: Proper process cleanup on Windows using CTRL\_BREAK\_EVENT signals
   \item \textbf{Config Persistence}: Placeholder-based configuration that works across environments
\end{enumerate}

\subsubsection{Layer Responsibilities}

\begin{description}
   \item[Domain Layer] Core business logic: \texttt{ServiceBase} (base class for microservices),
        \texttt{ServiceRegistry} (service registration and discovery), and \texttt{Factory}
        (component creation).

   \item[Ports Layer] Abstract interfaces defining contracts: \texttt{TransportPort} (message passing),
        \texttt{RegistryPort} (service registration), \texttt{UIBridgePort} (GUI communication).

   \item[Adapters Layer] Concrete implementations:
        \begin{itemize}
           \item \texttt{RabbitMQ Transport} -- RPC calls and message consumption via pika
           \item \texttt{RabbitMQ Registry} -- Service registration via exchange broadcasting
           \item \texttt{FastAPI Bridge} -- REST API, WebSocket, and Local Hub endpoints
           \item \texttt{Local Hub Manager} -- Process lifecycle management
           \item \texttt{Service Executor} -- Process execution with platform-specific shutdown
        \end{itemize}

   \item[GUI Layer] MicroserviceManagerGUI with dual hosting:
        \begin{itemize}
           \item \texttt{Electron} -- Desktop wrapper with contextBridge preload
           \item \texttt{Web} -- Pure browser-compatible HTML/CSS/JS
           \item \texttt{Service Plugins} -- Dynamically loaded per-service UI components
        \end{itemize}
\end{description}

\subsection{Components}

\subsubsection{ServiceBase}

The base class for all microservices provides:

\begin{itemize}
   \item API method discovery via \texttt{svc\_api\_} prefix convention
   \item Automatic service registration with the registry
   \item Graceful shutdown with \texttt{unregister\_service()} on exit
   \item Service info exposure for discovery via \texttt{\_SERVICE\_INFO} dict
   \item Docstring-based API documentation generation
\end{itemize}

\begin{verbatim}
from MicroserviceBase.domain.service_base import ServiceBase
from MicroserviceBase.factory import create_transport, create_registry

class MyService(ServiceBase):
    _SERVICE_INFO = {
        'name': 'MyService',
        'routing_key': 'service.myservice',
        'version': '1.0.0',
        'gui_support': False,
        'methods': [], 'methods_info': {},
    }

    def svc_api_my_method(self, arg1, arg2):
        """My API method."""
        return some_result

transport = create_transport('rabbitmq',
    cmd_args=['--host', 'localhost', '--port', '5672'],
    service_name='MyService')
registry = create_registry('rabbitmq',
    cmd_args=['--host', 'localhost', '--port', '5672'],
    service_name='MyService')

service = MyService(transport=transport, registry=registry)
service.register_service()
service.serve()
\end{verbatim}

\subsubsection{Service Properties (\_SERVICE\_INFO)}

Every microservice must define a \texttt{\_SERVICE\_INFO} class-level dictionary that describes
the service to the framework. The registry, the GUI, and the service creator all rely on
these properties. The following table lists every recognized key:

\vspace{0.5em}
\begin{center}
\small
\begin{tabular}{|l|l|c|l|p{5.5cm}|}
\hline
\textbf{Property} & \textbf{Type} & \textbf{Required} & \textbf{Default} & \textbf{Description} \\
\hline
\texttt{name}        & str  & yes & ---       & Unique service name (PascalCase recommended) \\
\texttt{description} & str  & no  & \texttt{''} & Full description, displayed in the Code Helper modal \\
\texttt{shortdesc}   & str  & no  & \texttt{''} & Short description shown in the GUI sidebar \\
\texttt{group}       & str  & no  & \texttt{''} & Category group for sidebar organization (e.g.\ \texttt{examples}) \\
\texttt{tag}         & str  & no  & \texttt{''} & Optional version tag \\
\texttt{version}     & str  & no  & \texttt{'1.0.0'} & Semantic version string \\
\texttt{routing\_key} & str & no  & \texttt{''} & RabbitMQ routing key for RPC requests \\
\texttt{gui\_support} & bool & no & \texttt{False} & Whether the service ships a GUI plugin
                                                        (\texttt{GUIs/} folder) \\
\texttt{downloadable} & bool & no & \texttt{False} & Whether the service exposes
                                                        \texttt{svc\_api\_get\_service\_files}
                                                        for remote download \\
\texttt{methods}      & list & auto & \texttt{[]} & \textit{Auto-populated} by \texttt{ServiceBase.\_\_init\_\_}
                                                       from \texttt{svc\_api\_*} methods \\
\texttt{methods\_info} & dict & auto & \texttt{\{\}} & \textit{Auto-populated} from method docstrings \\
\hline
\end{tabular}
\end{center}
\vspace{0.5em}

\noindent
Custom properties (e.g.\ \texttt{sample\_path}) may be added freely---the framework ignores
unknown keys but they are broadcast with the service info, so the GUI or other clients
can read them.

\paragraph{Example}

\begin{verbatim}
_SERVICE_INFO = {
    'name': 'ServiceCleware',
    'description': 'Service to control Cleware switch box devices.',
    'shortdesc': 'Cleware Controllers',
    'group': 'Switch Boxes',
    'tag': '',
    'version': '1.0.0',
    'routing_key': 'ServiceClewareKey',
    'gui_support': True,
    'downloadable': False,
    'methods': [],       # auto-populated at __init__
    'methods_info': {},  # auto-populated from docstrings
}
\end{verbatim}

\subsubsection{Generated Service Template}

The \textbf{Service Creator} wizard (or the \texttt{POST /api/scaffold/generate} REST endpoint)
produces a ready-to-run service package with the following file structure:

\begin{verbatim}
<ServiceName>/
|-- <service_name>.py     # Service class with _SERVICE_INFO and svc_api_* methods
|-- main.py               # Entry point: creates transport, registry, registers, serves
|-- __main__.py           # Enables: python -m <ServiceName>
|-- config.jsonp          # (EventBus only) transport configuration
|-- GUIs/                 # (if gui_support is enabled)
|   |-- service.html      # Bootstrap card template (or custom HTML)
|   |-- service.js        # IIFE with load/unload functions
\end{verbatim}

\paragraph{Service class (\texttt{<service\_name>.py})} contains the \texttt{\_SERVICE\_INFO}
dict with all metadata, and one \texttt{svc\_api\_*} method stub per API method defined in the
wizard. Each method stub includes a full docstring with \texttt{**Arguments:**} and
\texttt{**Returns:**} sections following the project convention.

\paragraph{Entry point (\texttt{main.py})} configures logging, creates the transport and
registry via the factory, instantiates the service, calls \texttt{register\_service()}, and
enters \texttt{serve()}. Graceful shutdown is handled in a \texttt{try/except/finally} block
that calls \texttt{unregister\_service()} and \texttt{close()}.

\paragraph{Package entry point (\texttt{\_\_main\_\_.py})} allows the service to be started
with \texttt{python -m <ServiceName>} from its parent directory, which is how the Local Hub
launches imported services.

\paragraph{GUI plugin (\texttt{GUIs/})} is only generated when the \textbf{Generate GUI template}
toggle is enabled in step~3 of the wizard. The HTML file provides a Bootstrap card layout
and the JS file exposes \texttt{load<ServiceName>()} / \texttt{unload<ServiceName>()} functions
using the \texttt{window.MicroserviceManager} namespace.

\subsubsection{Service Registry}

The registry manages dynamic service discovery:

\begin{itemize}
   \item Services register on startup with their method list and metadata
   \item Registry broadcasts updates to all subscribers via RabbitMQ exchange
   \item Shutdown notification via \texttt{\_\_registry\_shutdown\_\_} sentinel
   \item GUI receives real-time updates via WebSocket
\end{itemize}

\subsubsection{FastAPI Bridge}

The bridge connects the GUI to microservices:

\begin{description}
   \item[POST /api/request] RPC call forwarding to services
   \item[GET /api/services] Registered service list
   \item[WS /ws/updates] Real-time service update stream
   \item[/api/local-hub/*] Local process hub management endpoints
   \item[GET /docs] Auto-generated Swagger API documentation
\end{description}

\subsubsection{Local Hub Manager}

The Local Hub provides process lifecycle management:

\begin{itemize}
   \item Start, stop, and monitor local service processes
   \item Process configuration via \texttt{hub\_processes.json} with placeholder support
   \item Service import from folders or zip archives
   \item Service executor with graceful shutdown using \texttt{CTRL\_BREAK\_EVENT} on Windows
   \item Log file management per process
\end{itemize}

\subsection{Communication Patterns}
% ============================================================================

\subsubsection{RPC via RabbitMQ}

Services communicate using RPC (Remote Procedure Call) pattern through RabbitMQ.
The following diagram shows the complete communication flow between a service,
the Service Registry, and a client, including all exchanges and routing keys used:

\begin{figure}[!htb]
\centering
\includegraphics[width=0.85\textwidth]{pictures/sequence_communication.png}
\caption{Service Communication Flow (Exchanges, Queues, and Routing Keys)}
\label{fig:sequence_communication}
\end{figure}

\begin{verbatim}
from MicroserviceBase.domain.service_base import ServiceBase

# Client sends request
request_data = ServiceBase.create_request_data('svc_api_add', [1, 2])
response = transport.rpc_call(
    request_data,
    exchange_name='services_request',
    routing_key='service.calculator'
)
# response = {"request": "svc_api_add", "result": "pass",
#              "result_data": 3}
\end{verbatim}

\subsubsection{Service Registration}

Services register themselves via the registry exchange. The \texttt{ServiceBase}
class handles this automatically using the \texttt{\_SERVICE\_INFO} dict:

\begin{verbatim}
# ServiceBase auto-discovers svc_api_* methods and builds
# the service info dict, then publishes it:
service.register_service()

# On shutdown, unregister to notify the registry:
service.unregister_service()
\end{verbatim}

\subsubsection{Multi-Broker Architecture}

The GUI supports connecting to multiple RabbitMQ brokers simultaneously:

\begin{itemize}
   \item \texttt{MM.connections} map tracks per-broker state
   \item \texttt{serviceToBroker} reverse lookup for request routing
   \item Session persistence via \texttt{sessionStorage}
   \item Progressive disclosure: broker sections shown only when multiple brokers connected
\end{itemize}

\subsection{GUI Architecture}
% ============================================================================

\subsubsection{Dual Hosting}

The MicroserviceManagerGUI runs in two modes:

\begin{figure}[!htb]
\centering
\includegraphics[width=0.95\textwidth]{pictures/gui_architecture.png}
\caption{GUI Dual-Host Architecture (Electron + Browser)}
\label{fig:gui_architecture}
\end{figure}

\begin{description}
   \item[Electron Mode] Desktop application with native process management.
        Uses \texttt{contextBridge} preload for secure Node.js access.
        Can spawn and manage the FastAPI bridge process directly.

   \item[Browser Mode] Access via \texttt{http://localhost:1112} when the bridge is running.
        Pure HTML/CSS/JS with no Node.js dependencies.
        Uses the same \texttt{window.MicroserviceManager} namespace.
\end{description}

\subsubsection{Service Plugins}

Each microservice can provide a custom GUI plugin:

\begin{itemize}
   \item HTML file for UI layout
   \item JS file for logic (uses \texttt{const MM = window.MicroserviceManager;})
   \item Plugins loaded dynamically into \texttt{web/services/}
   \item In packaged mode, plugins extracted to writable \texttt{\%APPDATA\%} directory
\end{itemize}

\subsubsection{Standalone Installer}

The GUI can be packaged as a standalone Windows application using Electron Builder:

\begin{itemize}
   \item NSIS installer for Windows (\texttt{build.bat}), Linux packages (\texttt{build.sh})
   \item Read-only scripts in \texttt{resources/python/}
   \item Writable user data in \texttt{\%APPDATA\%/devatservgui/}
   \item First-run initialization copies templates and scripts
   \item Bridge process managed via PID file with detached mode
\end{itemize}

\subsection{GUI User Guide}
% ============================================================================

The Microservice Manager GUI provides three main tabs: \textbf{Services} for connecting
to brokers and interacting with microservices, \textbf{Service Network} for managing
the local process hub, and \textbf{Service Creator} for scaffolding new microservices.

% ----------------------------------------------------------------------------
\subsubsection{Connecting to a Broker}
% ----------------------------------------------------------------------------

To start using the GUI, click the \textbf{Connect} button in the top-right corner.
The connection dialog requires two fields:

\vspace{0.5em}
\begin{center}
\includegraphics[width=0.85\textwidth]{pictures/Services/01_Connect_Broker.png}\\[0.3em]
{\small\textit{Connect to Broker Dialog}}
\end{center}
\vspace{0.5em}

\begin{description}
   \item[Broker URL] The RabbitMQ broker address in \texttt{host:port} format
        (e.g., \texttt{localhost:5672}). The FastAPI bridge will connect to this
        broker to discover and communicate with services.
   \item[Routing Key] The routing key of the Service Registry
        (default: \texttt{ServiceRegistry}). This tells the bridge where to find
        the registry service that tracks all registered microservices.
   \item[Advanced Settings] Click the \textbf{Advanced Settings} link to reveal
        additional connection options such as exchange names and other
        broker-specific parameters.
\end{description}

After connecting, the GUI subscribes to real-time service updates via WebSocket.
The connected broker address appears as a badge in the top-right corner (e.g.\
\texttt{localhost:5672~x}). Multiple brokers can be connected simultaneously---each
broker appears as a separate section in the sidebar when more than one is active.

\begin{center}

\subsubsection{Local Service Hub}
% ----------------------------------------------------------------------------

The \textbf{Service Network} tab provides access to the Local Hub, which manages
service processes on the local machine. Switch to the \textbf{Local Hub} sub-tab
to configure and start the hub.

\vspace{0.5em}
\begin{center}
\includegraphics[width=0.85\textwidth]{pictures/ServiceNetwork/LocalHub/01_Start_Hub.png}\\[0.3em]
{\small\textit{Local Hub Configuration and Bridge Status}}
\end{center}
\vspace{0.5em}

The Local Hub configuration page provides the following options:

\begin{description}
   \item[Mode] Three radio buttons select the hub operating mode:
        \begin{itemize}
           \item \textbf{Standalone} --- runs an independent hub on this machine
                 (default).
           \item \textbf{Agent (join fleet)} --- connects to an existing fleet
                 orchestrator as a managed node.
           \item \textbf{Fleet Orchestrator} --- starts this hub as a fleet manager

        \end{itemize}

        \textbf{Stop Bridge} buttons to control the bridge process directly
        (Electron mode only).
   \item[Start Hub] Click to start the Local Hub. The hub reads
        \texttt{hub\_processes.json} and makes all configured services
        available for management.
\end{description}

\subsubsection{Local Hub Dashboard}

After starting the hub, the dashboard displays hub metadata, all configured

\vspace{0.5em}
\begin{center}
\includegraphics[width=0.95\textwidth]{pictures/ServiceNetwork/LocalHub/02_LocalHub_Dashboard.png}\\[0.3em]
{\small\textit{Local Hub Dashboard with Service Process Management}}

The dashboard header shows \textbf{Hub ID}, \textbf{Mode} (standalone / agent / orchestrator),
and the path to the loaded \textbf{Config} file. A toast notification confirms when the hub
has started successfully. The dashboard provides:

\begin{description}
   \item[Hub Controls] \textbf{Start All} and \textbf{Stop All} buttons to
        batch-control all services. \textbf{Reset} reloads the configuration.
        \textbf{Stop Hub} shuts down the hub and all running processes.
   \item[Service List] A panel labelled \textbf{Services (N/M running)} shows each
        configured service with its name, status (\textit{Stopped} / \textit{Running}),

        start (\,\raisebox{-0.1em}{\small$\blacktriangleright$}\,),

   \item[Connections] A side panel shows active broker connections with the

Services are started as subprocess with log file redirection. The hub uses
a two-phase graceful shutdown: first an RPC \texttt{svc\_api\_shutdown} call,
then \texttt{CTRL\_BREAK\_EVENT} (Windows) or \texttt{SIGTERM} (Linux),
and finally a force terminate if needed.

\vspace{0.5em}
\begin{center}

   \item The \textbf{Generated File Structure} preview shows the directory layout
         that will be created (e.g., \texttt{Test/test.py}, \texttt{Test/main.py},
         \texttt{Test/GUIs/service.html}).
   \item Specify an \textbf{Output Path} to save directly to disk, or leave empty
         to download as a ZIP file.
   \item Click \textbf{Download ZIP} to get the package as a zip archive, or
         \textbf{Save to Path} to write files to the specified directory.
\end{itemize}

The generated service package is ready to run. It can be imported into the
Local Hub using the \textbf{Import Service} feature, or started manually
via \texttt{python -m <ServiceName>} from the package directory.

\subsection{Process Configuration}
% ============================================================================

Processes are configured via \texttt{hub\_processes.json}:

\begin{verbatim}
{
    "ServiceRegistry": {
        "script": "${config_dir}/start_registry.py",
        "args": ["--config", "${config_dir}/config.json"],
        "process_name": "ServiceRegistry",
        "wait_time": 2.0
    },
    "Calculator": {
        "script": "${python}",
        "args": ["path/to/calculator.py"],
        "process_name": "Calculator",
        "wait_time": 1.0,
        "fleet_enabled": true
    },
    "ClewareService": {
        "script": "${python}",
        "args": ["-m", "ClewareService"],
        "cwd": "${config_dir}/services",
        "process_name": "ClewareService",
        "wait_time": 1.0,
        "service_name": "ServiceCleware"
    }
}
\end{verbatim}

\subsubsection{Process Properties}

Each entry in \texttt{hub\_processes.json} supports the following properties:

\begin{description}
   \item[script] Path to the executable or Python script.
        Supports \texttt{\$\{python\}} and \texttt{\$\{config\_dir\}} placeholders.
   \item[args] List of command-line arguments passed to the script.
   \item[process\_name] Display name used in the dashboard and logs.
   \item[wait\_time] Seconds to wait after spawning before checking if the process
        is still alive (default: \texttt{2.0}).
   \item[cwd] \textit{(optional)} Working directory for the process. Required when
        using \texttt{-m} module execution (e.g., \texttt{python -m ClewareService}).
   \item[env] \textit{(optional)} Dictionary of extra environment variables to set
        for the subprocess.
   \item[service\_name] \textit{(optional)} The RabbitMQ queue name the service
        consumes on. Used by the executor to send \texttt{svc\_api\_shutdown} RPC.
        Falls back to the entry key if omitted.
   \item[fleet\_enabled] \textit{(optional, default \texttt{false})} When \texttt{true},
        the process can be started and stopped remotely via Fleet orchestrator
        commands. Processes without this flag are protected from remote control
        (shown with a lock icon in the Fleet Hub detail view).
\end{description}

\subsubsection{Placeholders}

\begin{description}
   \item[\$\{python\}] Resolves to \texttt{sys.executable} at runtime
   \item[\$\{config\_dir\}] Resolves to the directory containing \texttt{hub\_processes.json}
\end{description}

Placeholders are preserved in \texttt{\_raw\_config} during save operations,
allowing the same configuration file to work across different environments.

\subsection{Windows Process Lifecycle}
% ============================================================================

On Windows, process shutdown requires special handling:

\begin{figure}[!htb]
\centering
\includegraphics[width=0.7\textwidth]{pictures/state_process_lifecycle.png}
\caption{Local Hub Process Lifecycle States}
\label{fig:state_process_lifecycle}
\end{figure}

\begin{itemize}
   \item \texttt{proc.terminate()} calls \texttt{TerminateProcess} which allows no cleanup
   \item Service Executor uses \texttt{CTRL\_BREAK\_EVENT} for graceful shutdown
   \item \texttt{signal.SIGBREAK} handler converts to \texttt{KeyboardInterrupt} for Python cleanup
   \item Pika's \texttt{start\_consuming()} replaced with \texttt{process\_data\_events(time\_limit=1)}
         loop for interruptible consumption
   \item \texttt{subprocess.PIPE} blocking prevented by using \texttt{FileHandler} instead of
         \texttt{StreamHandler} for logging in subprocess mode
\end{itemize}

\subsubsection{Create a Service}

\begin{verbatim}
import sys
from MicroserviceBase.domain.service_base import ServiceBase
from MicroserviceBase.factory import create_transport, create_registry

class CalculatorService(ServiceBase):
    _SERVICE_INFO = {
        'name': 'Calculator',
        'description': 'A simple calculator service.',
        'version': '1.0.0',
        'routing_key': 'service.calculator',
        'gui_support': False,
        'methods': [], 'methods_info': {},
    }

    def svc_api_add(self, a, b):
        """Add two numbers."""
        return int(a) + int(b)

transport = create_transport('rabbitmq',
    cmd_args=sys.argv[1:], service_name='Calculator')
registry = create_registry('rabbitmq',
    cmd_args=sys.argv[1:], service_name='Calculator')

service = CalculatorService(transport=transport, registry=registry)
service.register_service()
service.serve()
\end{verbatim}
