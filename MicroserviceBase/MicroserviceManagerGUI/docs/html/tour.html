How to run this tour

Nine stops, about 55 minutes with questions. Each stop says what to show, what to say, and what the audience should take away. Stops 1–3 are the operator's view, stop 4 is the one service developers came for, stops 5–7 are the parts that make the GUI worth having, and stop 8 sends everyone home with a working recipe.

Before the room fills up. Have these running and checked:
  • Consul with at least two services registered — one with a GUI, one without. The bench demo's cluster is ideal (Bench demo).
  • The bridge: green Bridge up chip in the ribbon.
  • A terminal in the repo root, for stop 7.
  • An editor open on one component.json, for stop 4.

0 · The shape of the thing

Say this first, before any screen.

The Manager GUI is a thin client. It owns no test logic and no device drivers. Everything it shows comes from somewhere else, and that is the whole point: a service that knows how to talk about itself gets a user interface without anyone writing one for it. 

  ┌─────────────────────────────┐
  │  Manager GUI  (the shell)   │   Electron app, or the same pages in a browser
  │  ribbon · navigators · bench│
  └──────────────┬──────────────┘
                 │  HTTP + WebSocket
  ┌──────────────┴──────────────┐
  │  FastAPI bridge             │   gRPC client, Consul client, Nomad client,
  │  :1112                      │   signal hub, composition store
  └───┬──────────┬──────────┬───┘
      │          │          │
   Consul      Nomad     services        gRPC (reflection or a .proto),
   :8500       :4646     anywhere        server streams, signal streams
  • The shell renders; it never opens a socket to a service itself.
  • The bridge is the only thing that speaks gRPC, Consul and Nomad. It runs on the operator's machine.
  • Consul answers “what is running, where, and is it healthy”.
  • Nomad answers “start it, stop it, show me its logs”.
  • The services are ordinary gRPC servers. They do not import anything of the GUI.

Takeaway: nothing in the GUI is wired to a particular test bench. Change what is registered in Consul and the GUI changes with it.

1 · First look

Show, in this order:

  1. The ribbon, three tabs. User is the daily work, Developer holds the tools that generate code, Administrator holds the infrastructure. A role sees one tab and can ignore the rest.
  2. The status chips. Bridge up with start and stop buttons, then Consul and Nomad. If a chip is red, nothing else on the screen can be trusted — say that out loud, it saves the audience an hour later.
  3. Connect. The Consul address the GUI reads. Several can be connected at once; the service list groups by agent.
  4. The left rail and the three navigators at the bottom: Services (one service at a time), Bench (many services on one stage), Project (a Robot Framework test project, from a plugin).
  5. Click a service. Two outcomes, and both matter:
    • A service that says nothing about a GUI gets a runtime card: address, tags, health, and an API explorer built from gRPC reflection. Useful, generic, free.
    • A service that declares one gets its own screen — the tiles in the screenshot above.
    • A folder may ship both a component and an older hand-written panel. The component opens by default, and Developer → Selected service → Classic panel switches that service to the other one and remembers it — useful while a service is being migrated, and a good live comparison to show the room.

Takeaway: every registered service is usable on day one; a service that wants a real screen declares one, and that is stop 4.

2 · Configuration

Everything configurable is a file or a field — no rebuild, no code. Show the settings dialog (the gear, top right), then this table.

The one that bites. The desktop app sends two different origins: null on its HTTP calls and file:// on its WebSocket handshakes. A hand-written allow-list that lists only one of them looks fine until live signals silently stay disconnected. The defaults for a loopback bridge include both — see the origin allow-list.

Takeaway: the GUI is configured the way a service is — files and environment variables, reviewable and diffable.

3 · Consul and Nomad

Show: Administrator → Consul, then Nomad. Both offer the same three choices, and the wording is worth repeating because it is the mental model:

  • Dev — the GUI starts a throwaway agent. For a laptop demo.
  • Config — the GUI starts an agent from your own .hcl. For a real bench.
  • Connect — the GUI touches nothing and only reads an agent that already runs. For a shared cluster.

Then submit a job: Submit Job, pick an .hcl, and watch the allocation appear, the service register in Consul, and the service appear in the left rail. That chain — job → allocation → Consul → the GUI — is the whole operational story, and it is worth doing live rather than describing.

Takeaway: the GUI replaces a row of terminals, without hiding what those terminals did. Every panel names the HTTP endpoint behind it.

4 · What a service has to provide

This is the stop service developers came for. Say the summary first: a service needs to do exactly two things — register, and declare a component. Everything else is optional.

4.1  Register in Consul (mandatory)

Whatever registers the service — ServiceRunner, a Nomad service stanza, or a direct API call — must give:

FieldWhy the GUI needs it
Namewhat the rail lists, and what a composition references
Address + portwhere the bridge sends gRPC. Use an address the bridge can reach — on a corporate laptop, 127.0.0.1 beats the host address, which a proxy may swallow
Health checkthe dot next to the name
Tags (optional)filtering and grouping
Meta.gui (optional)the folder of the component to show. Without it the service still works — it gets the runtime card

In the Python base that is one environment variable, for example HELLO_GUI=HelloService1.0.0, which lands in Consul as Meta.gui. The GUI then loads web/services/HelloService1.0.0/.

4.2  Declare a component (the manifest)

component.json is a service's user interface, written as data. No JavaScript, no build step, no release of the GUI. Walk the audience through this one, field by field: 

{
  "component": "operator.hello",          // <layer>.<name>, unique on a bench
  "version": "1.0.0",
  "layer": "operator",                    // operator | session | config |
                                          // execution | runner | signals | bits
  "title": "Hello",
  "requires": {
    "shell": "^2.3",                      // the shell API it was written against
    "capabilities": ["grpc.call"]         // what it is allowed to do
  },
  "binds": {
    "consul": "@self",                    // the service that declared it
    "grpc": "hello.v1.HelloService"       // the proto service its tiles call
  },
  "tiles": [
    { "id": "greet", "size": "1x1", "kind": "command-form",
      "call": "Greet", "form": { "name": "string" }, "resultPath": "message" }
  ],
  "renderer": "schema"
}

The tile kinds — the vocabulary a service has:

KindShowsNeeds
textfixed textnothing
live-statuslabelled values, polled from RPCs or streamed from signalsgrpc.call / signals.subscribe
command-forma typed form and the answer; the form can be built from gRPC reflectiongrpc.call
tablerows from an RPC, or static rowsgrpc.call
loga server-streaming RPC, line by linegrpc.call
run-statusa run's progress—
framethe service's own HTML page, sandboxedwhatever the page uses

Sizes on the four-column stage: 1x1, 2x1, 2x2, 4x1. Plugins add further kinds — signal-strip comes from the bundled charts plugin.

4.3  The rules, and why they exist

A manifest is checked before it is mounted; a broken one is refused with the rule it broke, and the rest of the screen keeps working. The rules that matter to the audience:

  • Declare what you use. An RPC without grpc.call, or a signal without signals.subscribe, is denied at run time. Declaring more than you use is a warning.
  • Bind by name, never by address. "consul": "@self" means “the service that shipped me”. A host or IP in a manifest is rejected outright — a component that hard-codes a machine is not portable.
  • Stay in your layer. The component id starts with its layer, and only the bits layer may name a device; anything above it names a signal.
  • Pin the shell. "shell": "^2.3". A component written for a newer shell is refused instead of half-working.

Lint it before shipping — the same check the GUI runs:

node tools/endo-lint.js web/services/MyService1.0.0/component.json

4.4  Optional: the service's own HTML

When tiles are not enough, a frame tile shows a page from the service's folder. It runs in a sandbox: its own process, an opaque origin, no access to the GUI's page, storage or network. It reaches the service only through window.endo.ctx, and only within the capabilities the manifest declared. If it hangs, its tile says so and nothing else on the screen notices.

4.5  Optional: live signals

A bench signal (bench.dut.temp.degC) is not an RPC. The bridge finds the signal-discovery service in Consul, holds one subscription per owning service, and fans values out to the tiles at up to ten a second. A service participates by being part of the signal graph — a component just names the signal: 

{ "label": "Temperature", "signal": "bench.dut.temp.degC", "unit": "°C", "digits": 1 }

4.6  The seven layers, and what exists today

The layer in a component id is not decoration: it says what kind of thing the component is, and the contract enforces it (only bits may name a device; above it, everything names a signal). The layers also map onto services that the architecture expects — and this is the question every audience asks, so answer it before they do:

LayerWhat belongs thereToday
bitsdevice-facing services: the chamber, a PSU, a UDS gatewaylive — the chamber on the demo bench
signalsthe signal graph and its discoverylive — the bench signals
operatorwhatever an operator drives directlylive — the hello service
sessiona session manager: which DUT, which run, which labelsreserved — no service yet
configa configuration manager: bench and service configurationreserved — no service yet
executiona test execution service: what is running nowreserved — no service yet
runnera test runner: Robot Framework runs and their resultspartly — tooling, not a service (below)

The capabilities tell the same story, and the shell is honest about it: a component may declare them all, but two of them are answered by stubs until the services behind them exist.

CapabilityWhat it grantsState
grpc.callcall the bound gRPC servicelive
signals.subscribestream signal valueslive (bridge signal hub)
signals.setwrite a setpointlive
session.read, session.labelread the current session, label a runstub — reads return nothing, labels are not stored
config.read, config.writeread and write configurationstub — per-user local storage, not shared
files.projectthe Robot Framework project folderlive, through the Test projects plugin
process.spawnstart a child processlive for window plugins on the allow-list only
What to say when someone asks “so where is the test runner / session manager / configuration manager?” Those are services in this architecture, not features of the GUI, and they do not exist yet. What already exists is everything they will need to appear without a single line of GUI code: a layer reserved for each, capabilities declared and enforced, a run-status tile kind that renders a run's flow, steps and current position straight from an RPC, and a session-layer slot at the top of a bench. On the Robot Framework side the tooling is already here — the Robot resources plugin generates typed keywords from a .proto folder, and the Test projects plugin manages the project those keywords are exported into. What is missing is the service that runs them and reports progress; when it registers in Consul with a manifest, it gets its screen like anything else.

Takeaway: a service ships JSON, and the GUI ships the rendering. Neither side has to be released for the other to change.

5 · The bench

One service at a time is the Services view. A bench puts the tiles of many services on one stage. Which ones, and in which order, is a composition: 

{
  "composition": "bench07/operator",
  "title": "Bench 07 · operator",
  "shell": "^2.3",
  "role": "user",
  "plugins": ["charts"],
  "components": [
    { "from": "consul", "service": "session-service" },
    { "from": "consul", "service": "testbench-device-psu", "tiles": ["out"] },
    { "from": "consul", "service": "cpp-psu", "gui": "PowerSupply2.0.1" }
  ],
  "order": ["session.header", "*", "@cpp-psu"]
}
  • Services are referenced by Consul name; a composition never copies a manifest, so a service that changes its tiles changes every bench that uses it.
  • tiles shows only part of a component; gui names the folder for a service that cannot declare one itself (the C++ runtime does not register Meta.gui yet).
  • order takes <component>/<tile>, <component>, @<service> and * for everything else.
  • role is the ribbon tab the bench opens on — the same services, a different screen per role.
  • A service that is missing, refused or has no GUI still keeps a slot saying why. A bench never goes blank because one service is down.

Takeaway: the screen a test engineer stares at all day is a reviewable file, not a build of the GUI.

6 · Plugins

A plugin extends the shell itself, where a component extends one service. Neither is how a session manager, a configuration manager or a test runner will arrive — those are services, and they get their screens the way every service does (stop 4.6). A plugin is for what the shell lacks: a new tile kind, a view, a tool. It can contribute tile kinds, navigators, stage views, dock sections, drawer tabs and ribbon commands. Show the dialog and point at three things:

  • What it adds is printed under each plugin (kinds: signal-strip, drawer.tabs: Chart).
  • How it runs: schema (data only), frame (sandboxed code), window (its own window and child processes).
  • The allow-list. A window plugin does nothing until someone ticks it on this machine. Turning a plugin off takes effect at once, and tiles that needed it say which plugin they need.

7 · Build a service live

Do this live — it is eight minutes and it lands every claim of the previous stops.

  1. Name it (step 1) and pick Python + gRPC (step 2).
  2. Give it two methods (step 3): one plain RPC, one server-streaming. Or import an existing .proto.
  3. Review and generate (step 4). Show the file tree in the preview before pressing the button.

The same thing from a terminal, for the CI-minded half of the room:

python -m MicroserviceBase.tools.scaffold_cli --config my_service.yaml

What comes out, and where the GUI part is:

MyService/
├── protos/my_service.proto
├── domain/            ports/            adapters/
├── main.py
├── deploy/my_service.nomad.hcl
└── ui/
    ├── MyService1.0.0/component.json   ← the manifest, already filled in
    └── README.md                        ← where to copy it

The generated manifest is not a stub: one command-form per unary RPC and one log per server-streaming RPC, in the bits layer unless the spec sets ui_layer. Copy the folder next to the other components, set the service's <PREFIX>_GUI to its name, deploy the generated job, and the service appears in the rail with its own screen.

The four-line version, for the slide at the end:
  1. Register in Consul, with Meta.gui.
  2. Ship component.json in that folder.
  3. Lint it.
  4. There is no step 4.

8 · Closing

Finish on the bench, because it shows all of it at once: services discovered through Consul, values over gRPC and over the signal stream, a command going out from a tile, a plugin drawing the strips, and a service's own HTML running where it cannot hurt anything. The Bench demo is the beat-by-beat script for that screen, if you want to hand the audience something to repeat.
