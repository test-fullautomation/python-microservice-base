About

MicroserviceBase
loading...
Manager GUI
loading...

A Python + C++ framework for building gRPC microservices with Consul-based service discovery and Nomad-based orchestration. The Manager GUI gives you a desktop UX over the FastAPI bridge: operate running services through their own GUIs, put several of them on one bench, inspect and call any service via gRPC reflection, scaffold new services, export them into Robot Framework or Temporal test projects and run the tests, and start / stop the Consul and Nomad agents.

Getting Started

Microservice Manager is a graphical interface for operating and building MicroserviceBase services. It runs as a desktop app (Electron) or in a browser; both use the same FastAPI bridge.

First steps

  1. Bridge — in the desktop app the bridge starts with the window; the Bridge LED on the User tab turns green. If it stays red, press ▶ next to it.
  2. Consul — User → Service registry → Connect and enter the Consul address (e.g. http://127.0.0.1:8500). No Consul running yet? Administrator → Consul agent starts one in dev mode.
  3. A service — click it in the left pane. Its GUI opens in the main area.

Dual hosting

  • Desktop (Electron) — native window, starts and stops the bridge for you, opens Graph Studio in its own window.
  • Browser — served by the bridge at http://localhost:1112 (python -m MicroserviceBase.adapters.ui_bridge.fastapi_bridge, then open the URL). Window plugins such as Graph Studio are desktop-only.

The ribbon

The navbar holds three ribbon tabs; each opens a band of commands grouped by task:

  • User — operate: Bridge (LED, start / stop), Infrastructure (Consul and Nomad LEDs; click one to open its agent view), Service view (Tiles or Service window, for a service that ships both), Bench (show the bench, pick a composition, Edit, Reload), Service registry (Connect, and one chip per connected Consul with × to disconnect). While the bench is shown, components add their own groups here.
  • Developer — build and test: Inspector (Developer mode), Build (Service Creator, Robot Resources, Graph Studio), Test project (Project view, Open project), Selected service (API Explorer, Code Examples, Add to project, Download files).
  • Administrator — configure: Service Network (Consul agent, Nomad agent) and Shell (Plugins).

The ribbon folds away to leave room for the content and drops down when you click a tab; the pin on the right keeps it open. Next to it: Report Issue (opens a pre-filled GitHub issue), this guide and Settings.

The left pane

The switcher at its bottom picks what the pane lists: Services (the connected registries), Bench (the modules of the shown composition) or Project (the files of the open test project). Switching never interrupts a running service GUI; coming back shows it exactly as you left it.

Services

The default view and where the app starts. The left pane lists every service registered in the connected Consul(s), grouped per registry when there is more than one. The search box filters by name; the dot shows the Consul health check (green passing, red failing).

What opens for a service

  • Its component — a service that declares a GUI with a component.json opens as tiles (status, command forms, tables, logs, framed panels). The badge at the top right says whether the manifest passes the contract.
  • Its classic panel — an HTML / JS, QML, Qt Widgets, Qt WASM or schema GUI. A folder that ships both opens the component; User → Service view → Tiles | Service window switches that service between the two, and the choice is remembered.
  • No GUI — the service is marked No GUI and shows an overview (health, instances with their checks, address, tags) plus an Actions section: one typed form per method, so operators can call it without developer tooling.

GUIs delivered by the service. When the GUI's folder is not on this PC yet, the Manager asks the service for it (services built on ServiceRunner serve their GUI over gRPC), unpacks it and opens it — so a fresh machine fills itself. Developer → Download files fetches it again.

Bench

User → Bench (or Bench in the left pane's switcher) shows the tiles of several services on one 4-column stage. Which services, in which order, is a composition; pick one in the Bench group.

  • Edit opens the composition. The Visual tab lists every connected service that declares a GUI, the composition's first and in its order: tick a service to show it, untick tiles to hide them (the tiles come from its component.json), drag a row by its handle or use ↑ ↓ to set the order, and give a GUI folder to a service that registers none. Every change is written to the JSON tab, which is what is checked against the contract and saved through the bridge; edit it directly for anything else. With nothing stored, the bench shows All components: every connected service that declares a GUI.
  • A module that cannot show tiles keeps its slot and says why (refused with the broken rules, classic panel, no GUI, not registered); the rest of the bench keeps working.
  • Selecting a tile opens the dock with the component's details and, when it lists one, its API explorer. The drawer below the stage has a Chart tab for the selected tile's signals.
  • Live signals update at most 10 times a second. They need signal-discovery in the connected Consul (or its address set with the signals badge under the stage).
  • Tiles stop polling while the bench is hidden.

Which services and tiles appear

A service declares a GUI by registering the name of its GUI folder in Consul as Meta.gui: the <PREFIX>GUI setting of the service, the same for Python and C++ services. The folder is web/services/<folder>/, and its component.json lists the service's tiles. All components takes every such service with all its tiles; a composition chooses: 

{
  "composition": "endurance/user",
  "title": "Endurance bench",
  "shell": "^2.3",
  "role": "user",
  "components": [
    { "from": "consul", "service": "testbench-climate-chamber-sim" },
    { "from": "consul", "service": "testbench-device-pps-mock", "tiles": ["output", "voltage"] },
    { "from": "consul", "service": "bits-power", "gui": "BitsPower1.0.0" }
  ],
  "order": ["@testbench-device-pps-mock", "*"]
}
  • components — the services on the bench, and only these (by their Consul name).
  • tiles (optional) — only these tiles of the service's component, by their ids in its component.json.
  • gui (optional) — the GUI folder for a service that does not register Meta.gui itself.
  • order (optional) — the order on the stage: @service (that service's module), component (all its tiles), component/tile (one tile), * for everything not listed.
  • shell — the GUI versions the composition works with, as a range (^2.3); a GUI outside that range refuses it, and so does a range left open (*).
  • role — user, dev or admin: the ribbon tab the bench selects while it shows this composition. A composition is stored per bench and role (endurance / user), and the picker lists them that way.
  • Compositions are stored per user in %APPDATA%\devatservgui\compositions\ (on Linux ~/.config/devatservgui/compositions/), or in the folder named by MB_COMPOSITIONS_DIR.
  • The role applies to a whole composition, not to single tiles; for a different selection per role, store one composition per role.

Developer tools

Developer mode (inspector)

Developer → Developer mode docks an inspector for the selected service with three tabs:

  • API — the methods from the server's reflection, each with a JSON request pre-filled from its schema and a Call button (server streams included). Also Code, Robot and Add to test project.
  • Details — instances, health checks, Consul metadata.
  • Code — ready-to-run client snippets in Python, C++ and Robot Framework.

API Explorer and Code Examples in the ribbon open the inspector on those tabs directly.

No reflection? Some servers (older builds, custom toolchains) don't ship grpc++_reflection. The bridge then compiles local .proto files; if it finds none, the panel asks for the folder that holds them and remembers it for the session.

Robot Framework resources

Developer → Build → Robot Resources turns a .proto folder into one .resource file per service, each with typed keywords (one per RPC) on top of QConnectBase.ConnectionManager. Existing files are skipped unless you confirm the overwrite. The same generator runs from the command line: 

python -m MicroserviceBase.tools.robot_gen --proto-dir <path> --out <path>

To export a running service straight into a test project instead, use Add to project (see Test projects). Long-form: Generate Robot Framework resources.

Signal Graph Studio

Developer → Build → Graph Studio opens the Signals & Blocks graph editor in its own window (desktop app only): draw blocks, wires and observe taps, generate a deployable graph service (configs, Nomad job), then watch it run — ◉ Monitor shows live values on the graph, the Chart tab plots them, and a setpoint block's inspector writes a value into the running service. Library… scaffolds new block types and regenerates the block catalog.

Test projects

A test project is a folder the Manager exports services into, so test authors get working keywords without copying generated files by hand. Its runner — chosen when the folder is initialized — decides the files and how tests run: Robot Framework AIO (suites, flows, keyword resources) or Temporal (Python SDK) (pytest tests running workflows, generated activities). The project view groups and names the files in the runner's words.

Open, browse, export

  • Open — Developer → Test project → Open project. A folder that is not a test project yet can be initialized with the runner of your choice (the one whose files it already holds is preselected); existing files are never moved or changed.
  • Browse — Project view (or Project in the left pane's switcher). Every file is marked gen (generated), starter, yours or manifest; an amber dot means a generated file was edited since the last export, a red dot that it was deleted.
  • Export a service — select it, then Developer → Add to project. You see a plan first — every file with its status and a diff for anything that would change — and nothing is written until you confirm. The overview's Re-export refreshes a service later.

Edit

Suites, starter files and your own files open in an editor with Robot Framework highlighting (Ctrl+S saves). Check (and every save) parses the file with Robot Framework and lists syntax problems by line. A save never overwrites a file that changed on disk since you opened it. Generated files and the manifest are read-only. New suite… creates a suite already wired to an exported service's keywords. The + on Flows creates a flow file (flows/<name>.flow.json) that imports the resource files you tick: one test with one step to replace, opened on its Diagram, ready for Edit flow.

Grid

Suites and resources also have a Grid tab: one row per step, the keyword it calls, then one cell per argument labelled with the parameter it fills. Keywords are resolved from the file’s imports the way the run resolves them; unknown keywords, extra values and missing required parameters are marked. Hover a keyword for its parameters and documentation; click a line number to find it in Script. Click a step to change it: pick the keyword (type a few letters — “sh be eq” finds Should Be Equal), then fill one input per parameter. + Add step, Insert step below, Delete step and Undo last change are there too; so are FOR / IF / WHILE / TRY (and, with RobotFramework AIO, THREAD) blocks and their branches, moving steps, settings, imports, variables, and adding, renaming and deleting tests and keywords. To put steps inside a block, click its END row (+ Add step here) or its first row (Inside). + Setting next to a test’s or keyword’s name adds its own [Documentation], [Tags], [Setup], [Teardown], [Timeout], [Template] or [Arguments]. Typing ${ in a value offers the variables in scope. Changes land in Script as unsaved edits.

Flow files

Flow files (*.flow.json, listed under Flows) are test plans drawn as a graph; RobotFramework AIO's flow support turns them into a suite when they run. They open with three tabs:

  • Script — the JSON, the only thing you edit.
  • Diagram — the flow drawn from the text in Script, unsaved changes included: a lane per phase, gates as hexagons, loops and tries as frames with their recovery, decisions with their yes / no branches, a sub-flow (a call of another flow file) as a box with a bar on each side whose + opens its steps in place. Click a node to find it in Script. Drawn by the Flow view plugin; with the plugin off, the tab says so.
    Edit flow (above the drawing, while the file is open in Script) changes the flow by drag and drop:
    • drag a step from the palette — Keyword, Gate, Sleep, Sub-flow, Decision, Loop, Try, Test — onto a + to add it there (a new loop or try comes with a No Operation step to replace; a sub-flow asks for its file);
    • drag a step onto another + to move it;
    • click a step for its fields — Apply changes them, Delete removes it (a loop or try with everything in it), Wrap in loop / Wrap in try puts it in a new one; Delete and Esc work too;
    • Undo puts back the text before the last change.
    Every change goes through the runner, which rewires the flow and checks it before it is accepted — a change that would break the flow is refused with the reason, and the file stays as it was. Accepted changes land in Script as unsaved changes: Script, the diagram and the run always read the same text.
  • Robot — the suite the flow becomes (read-only).

A flow the runner refuses shows its message with a link to the node or line it names.

Run

  • ▶ next to a suite or flow (on hover), Run… in its editor, or Run all… on the overview. The dialog takes variables for this run (NAME=value, one per line) and Dry run; both are remembered per file.
  • Runs shows the live console, then the verdict — Pass, Fail, Unknown (the bench was not ready, e.g. a gate timed out, so nothing was tested), Skipped or Error — one row per test, Log and Report, Run again and the history of earlier runs.
  • Stop ends a run gracefully (teardowns still run, reports are written); Force stop kills it. One run per project at a time.
  • Run settings… are kept in testproject.json so the project runs the same for everyone: interpreter, PYTHONPATH (e.g. the src of a RobotFramework AIO checkout), extra arguments, environment.

Each run gets its own folder, results/<date-time>_<name>/, so the history survives restarts.

Pause, resume, continue (flows)

  • Pause holds a running flow at the next step boundary (deadlines and timeouts wait too); Resume goes on. For a run group, each member can also be paused alone.
  • Stop on a flow writes a checkpoint; Continue from checkpoint then starts a run that skips the finished phases and goes on with the interrupted loop.
  • Step mode in the Run dialog pauses before every step; Next step goes one step on.

Debug

  • Debug next to Run… runs a suite or flow under the debugger. Click a line number in the editor, or the dot on a step of the Diagram, to set a breakpoint.
  • When it stops, Runs shows the source at the line, the call stack, the variables and a console (${var}, a keyword call, or a Python expression when stopped in Python). Continue (F5), Step Over (F10), Step Into (F11 — also into the Python function of your own library's keyword), Step Out (Shift+F11), Pause, and Stop when a keyword fails.
  • Go to Definition: F12 or Ctrl+Click on a keyword, an import or a sub-flow in the editor.

Run groups

Processes that run at the same time and wait for each other through the bench — two blades running one flow with different variables, or a driver and a checker. Run groups in the sidebar lists them; + creates one: 2–8 members, each a file of the project with its own variables, plus environment for all of them (${RUN_DIR} is the run’s own folder, a fresh meeting place per run).

  • Diagram — one column per member, read top to bottom, and a dashed arrow wherever a step of one member sets a signal that a gate of another waits for (read from the flows). Click a step to open its file there.
  • ▶ / Run… starts every member at once; Runs shows a console column per member with its own verdict, Log and Report. The run’s verdict is the worst of theirs; Stop stops them all.

Resources of a run

Tick Record RAM and CPU of the run in the Run dialog (off by default) and a separate process samples RAM and CPU of every process of the run every 5 seconds. When the run ends, Resources (next to Log and Report) opens resources.html: a verdict per process — STABLE, GROWING (memory rising more than 10 MB/h after the warm-up) or SHORT (too short to judge) — with charts of memory, CPU, threads and handles over time. MM_RESMON_INTERVAL in the run settings' environment changes the interval.

Live Diagram of a run

A run of a flow file or of a group of flow files shows its Diagram beside the console: the step each process is in pulses in blue, the loop around it is outlined, a step that just failed turns red for a moment, and every step counts how often it passed (✓) and failed (✗). The Diagram button in the tab row hides or shows it; drag the divider (or use the arrow keys on it) to share the width; Fit / 75% / 100% size the drawing. It follows the running step unless you have just scrolled it. The steps passed between two updates (about a second apart) replay quickly: Tail flashes them in order and lets them fade, Hop moves the mark through them, Off shows only the current step. After the run the counts stay.

Service Creator

Developer → Build → Service Creator scaffolds a new service project (proto, domain, adapters, clients, Nomad job and a starting component.json) without writing boilerplate.

  1. Basic Info — name, version, description, group, tag, routing key and transport.
  2. Technology — language (Python / C++), GUI type, the layer its Manager GUI component belongs to, and the toolchain: for C++ the server's gRPC build (MSYS2 or vcpkg + Qt MinGW) and a matching client stack.
  3. API Methods — define RPC methods by hand, or Import .proto… (multi-service protos get a picker and a single-project / monorepo choice).
  4. GUI Support — only for Python services with an HTML / JS GUI; skipped otherwise.
  5. Review & Generate — preview the file tree, then write it to the folder you pick.

The wizard drives the same generator as the mb-scaffold CLI; for scripted use: python -m MicroserviceBase.tools.scaffold_cli -c spec.yaml. Long-form: Service Creator wizard.

Service Network (Consul + Nomad)

Administrator → Consul agent or Nomad agent opens the Service Network view on that tab. It replaces the per-terminal consul agent -dev / nomad agent -dev workflow.

Consul tab

  • Not running — three ways in: Dev Mode (single node, in memory), Config Directory (load .hcl / .json) or Connect to Existing (the URL of a running agent).
  • Connected — leader, nodes, the registered services with their healthy instances, plus Open Consul UI, Disconnect and Stop Agent.

Defaults match the framework: HTTP port 8500, datacenter dc1.

Nomad tab

  • Counters — total, running, pending and dead jobs, nodes ready.
  • Jobs table — every job with its type, status and task groups; each row links to its detail.
  • Submit Job — HCL or JSON; Load from file… picks e.g. a generated deploy/<svc>.nomad.hcl, or paste the content.
  • Open Nomad UI — the agent's own UI in a browser window.

Dev Mode writes a configuration with raw_exec enabled, so generated jobs (driver = "raw_exec") run on Windows. Long-form: Operating Consul + Nomad.

Plugins

Plugins extend the GUI itself: tile kinds, tabs, views and ribbon commands. Administrator → Shell → Plugins lists them and turns them on or off on this PC; the change takes effect at once.

Robot resourcesRobot Resources in the Developer tab's Build group
Signal Graph StudioGraph Studio in the Build group; opens its own window (desktop app only)
Test projectsthe Project view, the Project entry in the left pane, the Test project ribbon group
Flow viewthe Diagram tab of flow files and run groups in the project view
Robot gridthe Grid tab of suites and resources in the project view
Chartsthe signal-strip tile kind and the Chart drawer tab on the bench
  • Turning a plugin off removes what it added; tiles of its kinds and views it draws say which plugin to turn on.
  • Plugin code runs in sandboxed frames, apart from the rest of the GUI. Plugins that open their own window and may start processes (Graph Studio) run only when they are on the allow-list, set in the same dialog.
  • Installed plugins live in %APPDATA%\DevAtServGUI\plugins\<id>\ and win over a bundled plugin of the same id.

Settings

The in the navbar opens them:

  • View — what the GUI offers, as roles you combine:
    • User (always on): the Services and Bench views.
    • Administrator: the Administrator tab — Consul, Nomad (start agents, submit and stop jobs) and the plugin manager; the Consul/Nomad status pills open them.
    • Developer: the Developer tab — Service Creator, test projects, the plugin views (such as Project) and the inspector.
    It takes effect as soon as you save. In settings.json it is the view key: "user", "user+admin", "user+developer", "user+admin+developer" (or "all"; a list such as ["user", "admin"] works too). Without the key the GUI shows everything. A browser-hosted GUI can also be opened with ?view=user+admin in its address, which wins over the setting. The view tidies the GUI for its audience; it does not restrict what the bridge allows.
  • Python Path — the interpreter the desktop app starts the bridge with; also the default interpreter for test runs.
  • Consul executable / Nomad executable — used when starting a local agent from the Service Network view. Looked up in this order: this setting, PATH, %ProgramFiles%\HashiCorp\. Leave empty to use PATH.
  • Broker Host / Broker Port — the RabbitMQ broker of the legacy transport.
  • Bridge Port — where the FastAPI bridge listens (default 1112).

Troubleshooting

Quick lookups. For the full symptom-indexed reference see Troubleshooting in the repository docs (docs/reference/troubleshooting.md).

Bridge LED stays red

The bridge didn't start. In the desktop app press ▶ next to the LED (User tab). If port 1112 is taken, free it (netstat -ano | findstr :1112) or change Settings → Bridge Port.

"Reflection RPC … failed: UNIMPLEMENTED" when clicking a service

The server doesn't ship grpc++_reflection. The panel offers a proto-path field — enter the folder containing the service's .proto and click Use this path. Permanent fix: rebuild the server with reflection enabled (the latest vcpkg overlay port forces this; re-run init_vcpkg_overlay.bat --upgrade).

A tile or bench slot says "refused"

The component's manifest breaks a contract rule; the slot lists the rule ids. Check it before shipping with node tools/endo-lint.js web/services/<gui>/component.json in the Manager GUI folder.

A tile says "enable the plugin", or a Diagram tab says a plugin is off

The plugin that provides it is turned off on this PC. Turn it on under Administrator → Plugins.

Service registers, then disappears from Consul ~30 seconds later

The Consul health check is failing. Check nomad alloc logs <alloc-id> — the service likely crashed or never started gRPC. Confirm <PREFIX>_GRPC_PORT was set in the environment (Nomad sets it via ${NOMAD_PORT_grpc}).

Nomad job stays "pending" forever

Most often a driver mismatch. Generated jobs use raw_exec; dev mode enables it. Custom config? Add the raw_exec plugin block. Or check nomad node status for a healthy client — and that the job's constraints match one.

"Port 8500 in use" when starting Consul (or 4646 for Nomad)

Another agent is running. Either stop it (tasklist | findstr consul → taskkill /pid <pid>) or use the tab's Connect to Existing form to point at it.

A flow's Diagram or Robot tab says the runner's tools are missing

The project's interpreter can't import RobotFramework AIO's flow support. Open Run settings… and set the interpreter, or add the src of a RobotFramework AIO checkout to PYTHONPATH.
