## Context

Python services in this framework historically used:

- A system-installed Python at `C:\Program Files\RobotFramework\python3\`
  (per the project memory note about non-editable installs)
- `pip install` against site-packages, which made every service share
  one global dependency tree

Problems:

- **Dependency conflicts** — Service A wants `grpcio==1.60`, Service B
  needs `grpcio==1.50`.  Both can't coexist in one site-packages
- **No reproducibility** — `pip freeze` output drifts; no lockfile
- **Slow installs** — `pip` is single-threaded and resolution-heavy
- **Non-editable install of MicroserviceBase itself** (memory note)
  meant local dev edits required a re-install before the bridge would
  see them — friction every loop

The TA reference adopts **uv** (Astral's Rust-written package manager)
with a per-service venv and a checked-in lockfile.  uv is 10-100x
faster than pip, has a single-binary install, and produces
reproducible `uv.lock` files.

## Decision

Each Python service gets its **own uv-managed venv** rooted at the
service folder.  Generated by the scaffold; activated by the wrapper
script (ADR-025).

- **`pyproject.toml`** declares dependencies (the standard
  `[project] dependencies = [...]` table)
- **`uv.lock`** is checked in — pins exact versions for reproducibility
- **`.venv/`** lives next to `pyproject.toml`; **gitignored**
- **`uv sync`** is run at scaffold time and as a CI / deploy step;
  produces `.venv/` from `uv.lock`
- **`uv run <cmd>`** is the canonical way to invoke service scripts
  during development; the wrapper script does the equivalent (PATH
  munging) at runtime

The MicroserviceBase package is installed into each service's venv as
either:

- **Editable (`uv pip install -e D:\Project\robot\...`)** for local
  development — picks up source edits immediately
- **Pinned wheel** for production — built once, distributed via the
  internal artefact store (when set up)

This replaces the "install MicroserviceBase into the system Python"
pattern that caused the memory-note friction.

## Consequences

### Positive

- **No more dependency-conflict roulette** — each service is an island
- **Reproducible builds** — `uv sync` from `uv.lock` produces an
  identical venv on any machine
- **Fast** — uv resolves and installs in seconds, not minutes
- **Editable installs work** — `uv pip install -e ...` lets dev edits
  to MicroserviceBase land without a re-install cycle (fixes the
  long-standing friction note)
- **Aligns with TA reference and the broader Python ecosystem** — uv
  is becoming the default tooling for new Python projects

### Negative

- **uv is a new tool** for the team — learning curve, even if small
- **uv binary distribution** — operators need uv on every Nomad client
  (fold into the client provisioning script; a single
  `winget install astral-sh.uv` or `curl ... | sh` line)
- **Migration cost** — existing services need a `pyproject.toml` +
  `uv sync` pass.  Automated by a one-shot script in
  `tools/migrate_to_uv.py` (to be written)

### Neutral

- C++ services aren't affected — vcpkg already gives them per-project
  dependency isolation.  uv is the Python-side analogue

## Alternatives Considered

### 1. Stick with pip + global site-packages (Rejected)

The current state.  Caused every problem in the Context section.

### 2. pip + per-service venvs (Acceptable but worse)

Solves dependency conflicts.  Doesn't fix slow installs, doesn't give
us a lockfile, and doesn't align with the TA reference.

uv is strictly better at the same job.

### 3. Poetry (Rejected)

Has lockfiles + per-project venvs, similar value proposition.

Rejected because:
- TA reference uses uv — staying consistent reduces cognitive load
- uv is faster
- uv's CLI surface is smaller and closer to pip's

### 4. Conda / mamba (Rejected)

Powerful for scientific stacks.  Overkill here; we mostly need pure
Python + a few wheels (grpcio, protobuf, fastapi).
