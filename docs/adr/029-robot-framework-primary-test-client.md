## Context

The framework's services are built to run automated tests against
hardware (PPS, signal generators, scopes, HIL boxes).  Until now the
"how do you actually drive the services from a test" story has been
implicit:

- C++ tests via `qt_client_grpcpp` example (one-off integration
  scripts)
- Python tests via `LocalProtoClient` with hand-written test scripts
- GUI's API Explorer for interactive ad-hoc calls

What's missing is a **canonical test-authoring path** for the people
who actually write tests — testers and engineers who aren't paid to
write C++ or to wrangle gRPC channels.

The TA reference standardises on **Robot Framework**: a keyword-driven
test framework with a syntax that non-developers can read and write,
plus a library ecosystem that includes gRPC support.

This is the right fit because:

- Bosch / BITS has existing Robot Framework expertise and infrastructure
- Robot test logs are auditable — keywords + arguments + pass/fail are
  legible to non-engineers
- Adding new keywords (Python functions exposed as Robot keywords) is
  straightforward; testers don't have to write gRPC plumbing

## Decision

**Robot Framework is the primary test-authoring entry point**, with
the framework providing a Robot library that wraps gRPC services
behind keywords.

Components:

- **`MicroserviceBaseLibrary`** — a Python package that exports Robot
  keywords like `Connect To Service`, `Call Method`, `Stream
  Telemetry For`, etc.  Internally uses `LocalProtoClient` (which
  itself uses gRPC reflection from ADR-028)
- **Per-service keyword libraries** — generated by the scaffold for
  each service.  Each `.proto` method gets a Robot keyword:
  `ServicePps.Set Voltage    12.0V`
- **Test repo layout** — Robot tests live in a separate repo (or a
  `tests/` subfolder for scaffold-generated services); they import
  the keyword libraries and run via `robot` CLI
- **CI integration** — Robot's `output.xml` + `report.html` artefacts
  fold into CI's existing test-result viewer
- **Discovery** — Robot tests don't hardcode service host:port; they
  pass a Consul agent address and let the keyword library resolve via
  Consul (ADR-023)

This does **not** replace direct-gRPC testing for unit tests inside
the service repo (e.g. C++ gtest against the in-process gRPC server).
Robot Framework is for **integration / system tests** that drive
real services over the network.

## Consequences

### Positive

- **Tests are written by the people who should write them** — testers,
  not service developers
- **Test logs are legible** — Robot's HTML report is shareable with
  non-technical stakeholders
- **Reuses framework infrastructure** — Consul resolution, gRPC
  reflection, Kafka subscription all exposed as keywords
- **Aligns with TA reference and Bosch test-authoring conventions**

### Negative

- **Two test ecosystems to maintain** — gtest/pytest for unit tests
  + Robot for integration tests.  But this is the existing reality
  in any non-trivial project
- **Robot's syntax is opinionated** — engineers used to xUnit
  patterns may resist.  Mitigated by giving them pytest for unit
  tests and reserving Robot for the integration layer
- **Generated keyword libraries can drift** from .proto changes —
  scaffold needs a "regenerate keyword library" step that runs
  whenever .proto files change

### Neutral

- The Manager GUI's API Explorer remains useful for *interactive* ad-hoc
  calls — Robot is for *scripted* tests.  Different tools, different jobs

## Alternatives Considered

### 1. pytest + custom fixtures (Acceptable but worse)

Engineers can write integration tests in pytest using gRPC clients
directly.

Worse because:
- Not accessible to non-developer testers
- No standard reporting format usable by stakeholders
- Each project reinvents fixtures for service connection / Consul
  resolution

### 2. xUnit-family in C++ (Rejected for integration tests)

Fine for unit tests inside a C++ service.  Wrong tool for cross-service
integration tests where the test author isn't the service author.

### 3. Custom DSL (Rejected)

Could write a microservice-base-specific test DSL.

Rejected because:
- Robot Framework is already a mature DSL with most of what we need
- Bosch testers already know Robot
- Inventing a DSL is a multi-quarter project

### 4. Cucumber / Gherkin (Rejected)

Similar value proposition to Robot.

Rejected because:
- Less ecosystem support for gRPC clients in Cucumber
- TA reference uses Robot — consistency wins
