## Context

Nomad's `raw_exec` driver runs a single executable per task with a
fixed env block and no shell-level setup.  Real services need more:

- **PATH must include** vcpkg-deployed DLL folders, MinGW runtime,
  Qt's `bin/`, and (for Python services) the project's uv venv
  `Scripts/`
- **Working directory** has to be the service folder so relative paths
  in config files resolve
- **Environment variables** like `<PREFIX>_GRPC_PORT`,
  `<PREFIX>_CONSUL_ADDR`, `<PREFIX>_ADVERTISE_ADDR` need to be
  computed from the Nomad-allocated `NOMAD_PORT_grpc` and the local
  Consul agent's address
- **Signal handling** on Windows requires `CTRL_BREAK_EVENT`, not
  `SIGTERM`, and child processes need to inherit the right console
  group
- **Pre-flight checks** (DLL availability, port reachability, Consul
  agent liveness) make failures diagnosable before the service tries
  to register

Putting this in the Nomad job HCL via dozens of `env {}` lines and a
brittle inline `args` array doesn't scale and can't run pre-flight
checks.

The TA reference solves this with a **wrapper script** that Nomad
launches; the wrapper sets up the environment and exec's the real
service.

## Decision

Adopt a **wrapper layer** between Nomad's `raw_exec` driver and the
service process.  Each generated service ships two wrappers:

- `run_<svc>.bat` — Windows wrapper, called by `cmd.exe /c run_<svc>.bat`
- `run_<svc>.sh` — Linux wrapper, called by `bash run_<svc>.sh`

The wrapper:

1. **Sets `PATH`** — prepends vcpkg `bin/` (Windows DLLs), MinGW runtime
   if applicable, Qt's `bin/`, and the uv venv `Scripts/` (Python)
2. **Sets the service's env vars** — derives `<PREFIX>_GRPC_PORT` from
   `NOMAD_PORT_grpc`, `<PREFIX>_CONSUL_ADDR` from `127.0.0.1:8500`
   (the local Consul agent), `<PREFIX>_ADVERTISE_ADDR` from
   `NOMAD_IP_grpc`
3. **Pre-flight check** — verifies the Consul agent is reachable; logs
   a clear error and exits with a distinct exit code if not (so Nomad
   doesn't restart-loop a misconfigured client)
4. **`cd`s** into the service folder
5. **Exec's the service binary** — via `exec` (Linux) or
   `start /B /WAIT` (Windows) so signals propagate cleanly
6. **Forwards exit code** to Nomad

Generated by the scaffold (`adapters/scaffold/cpp_tmpl.py` for C++,
`adapters/scaffold/python_tmpl.py` for Python) — not hand-written
per service.

```
Nomad client
   │ raw_exec: cmd.exe /c run_pps.bat
   ▼
run_pps.bat   (wrapper)
   │ set PATH=vcpkg\bin;mingw\bin;qt\bin;%PATH%
   │ set PPS_GRPC_PORT=%NOMAD_PORT_grpc%
   │ set PPS_CONSUL_ADDR=127.0.0.1:8500
   │ ping consul agent ... ok
   │ cd C:\nomad\data\alloc\<id>\pps
   │ start /B /WAIT pps_service.exe
   ▼
pps_service.exe   (real service)
```

## Consequences

### Positive

- **Job HCL stays small** — the HCL doesn't have to know about vcpkg
  layout, uv venvs, or per-service PATH gymnastics
- **Pre-flight failures are diagnosable** — clear log line +
  distinct exit code, vs. the service silently failing to register
- **Cross-platform parity** — `.bat` on Windows, `.sh` on Linux, both
  generated from the same scaffold
- **Reproducible across machines** — the wrapper is the canonical
  source of "how to launch this service"; no machine-specific tribal
  knowledge

### Negative

- **One more layer to debug** — when a service fails, you check the
  wrapper log first, then the service log
- **Generator complexity** — scaffold templates emit two wrappers per
  service; both must stay in sync
- **Signals on Windows** — propagating `CTRL_BREAK_EVENT` from the
  `cmd.exe /c run_*.bat` shell down to the service process needs the
  right `start` flags; documented in the wrapper template

### Neutral

- The wrapper is also useful for **manual local runs** outside Nomad
  — `run_pps.bat` works from a developer shell with sensible defaults
  for `NOMAD_PORT_grpc` etc.

## Alternatives Considered

### 1. Push everything into Nomad job HCL `env {}` blocks (Rejected)

Possible, but every service ends up with a hundred-line `env {}` that
bakes in path layout choices.  Pre-flight checks aren't expressible
in HCL.

### 2. Use Nomad's `exec` driver with a chrooted filesystem (Rejected)

`exec` driver doesn't run on Windows.  raw_exec is what we have.

### 3. Custom Nomad task driver plugin (Rejected)

Could write a `microservice_base` driver that wraps `raw_exec`.

Rejected because:
- Plugin maintenance burden — has to track Nomad's plugin API
- Wrapper scripts are debuggable by anyone who reads bash/batch
- TA reference uses script wrappers; staying consistent with
  upstream design is cheaper

### 4. systemd / Windows Services (Rejected)

Was the LocalHubManager era pattern.

Rejected because Nomad's whole point is *being* the supervisor.
Layering systemd underneath fights it.
