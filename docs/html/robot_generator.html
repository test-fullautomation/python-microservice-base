Generate Robot Framework resources from a .proto folder

One .resource per service, one typed keyword per RPC — wrapping QConnectBase’s GrpcClient

Why this exists

Without this feature, every gRPC call from Robot Framework had to be written as a JSON-string send_cmd: 

${res}=    conn_manager.verify    conn_name=device
...                                 send_cmd={"method":"SetInterfaceType","args":{"type":0}}

With the generator:

${res}=    Com Setup Device Service Set Interface Type    conn=device    type=0

The generated keywords are service-prefixed (so two services with same-named methods can co-exist), use ${conn_name} as the first positional argument (so one test suite can target multiple deployments), and ship Open Connection / Close Connection helpers (named so they can’t collide with proto-defined Connect() / Disconnect() RPCs).

What you get

For every service declared in any .proto under your folder, the generator emits <snake_service_name>.resource with:

SectionContents
*** Settings *** Library QConnectBase.ConnectionManager (as conn_manager) + Library Collections.
*** Variables *** One per-service ${<SERVICE>_FQN} constant carrying the fully-qualified proto service name.
*** Keywords *** <Service> Open Connection / <Service> Close Connection helpers + one typed keyword per RPC.

Keyword conventions

ConventionWhy
Prefixed names — <Service> <Method> Two services with same-named methods co-exist in one suite.
${conn_name} first on every keyword Lets one test open N connections to different deployments and target each call.
Open Connection / Close Connection helpers Proto services frequently declare Connect() / Disconnect() RPCs. Helper names that shadow those would collide. Unambiguous spelling avoids that.
Single-space-only keyword names Robot’s parser treats 2+ consecutive spaces as a delimiter and truncates names. The converter dedupes underscores at camelCase boundaries so this can never happen.
No-arg RPCs skip the args-dict scaffolding RPCs with Empty requests render as a single verify with a constant send_cmd — no Create Dictionary, no Evaluate json.dumps.

Triggering generation

From the GUI

  1. Open a gRPC service in the Manager GUI (Service Network → click a registered service).
  2. Click the green Generate Robot resources button in the top-right of the methods panel. It’s always visible — works whether methods were discovered via reflection or by compiling a local .proto folder.
  3. If you haven’t provided a proto folder yet, a native folder picker asks for one.
  4. A second native folder picker asks for the output folder (defaults to a sibling robot/ directory next to your proto/ folder).
  5. Existing .resource files are skipped unless you confirm the overwrite dialog.
  6. Success toast: “Wrote N .resource file(s) to …”.

From the CLI (no bridge required)

"C:\Program Files\RobotFramework\python3\python.exe" -m MicroserviceBase.tools.robot_gen ^
    --proto-dir D:\projects\TestService\proto ^
    --out       D:\projects\TestService\robot
FlagMeaning
--proto-dir DIR (req.) Folder containing *.proto (non-recursive).
--out DIR Folder to write .resource files into. Required unless --stdout.
--service NAME Repeatable. Only emit resources for these services.
--force Overwrite existing files.
--stdout Print every generated resource to stdout (useful for diffing).

From the bridge HTTP API

POST /api/scaffold/robot
Content-Type: application/json

{
  "proto_dir": "D:/projects/TestService/proto",
  "out_dir":   "D:/projects/TestService/robot",
  "force":     false,
  "services":  []
}
  • out_dir empty → response carries { files: { "<rel>": "<content>" } } (caller persists them — used by the GUI button).
  • out_dir non-empty → response carries { written: [...], skipped: [...] }.

Using the generated resource in a test

*** Settings ***
Resource    com_setup_device_service.resource

*** Test Cases ***
SetInterfaceType Smoke
    Com Setup Device Service Open Connection    conn=device
    ...    service_name=multi_proto
    ...    consul_addr=http://127.0.0.1:8500
    ...    proto_dir=${CURDIR}/../proto

    ${res}=    Com Setup Device Service Set Interface Type    conn=device    type=0
    Should Be Equal As Integers    ${res}[errorcode]    0

    [Teardown]    Com Setup Device Service Close Connection    device

The proto_dir argument is forwarded to QConnectBase's GrpcClient and only consulted when the server lacks gRPC reflection. When reflection works, leave it empty.

Proto3 default-value quirk — fixed bridge-side. A successful RPC returning errorcode = 0 would normally surface as an empty {} dict (proto3 omits scalar fields holding their default value). The bridge now opts into always_print_fields_with_no_presence=True, so ${res}[errorcode] reliably resolves to 0. No action needed in your tests — just restart the bridge after the fix landed.

Troubleshooting

SymptomLikely cause / fix
Failed: Failed to fetch Bridge not reachable on the configured port. Restart the Manager GUI or check the Bridge LED in the navbar.
Reflection unavailable … no .proto files matched in search paths Server has no reflection AND no proto folder is set. Click “Provide a .proto folder” and type the folder, OR set MB_PROTO_SEARCH_PATH in the bridge env.
protoc returned exit code 1 for sources […] Auto-glob is picking up duplicate google/protobuf/*.proto from build directories. Set an explicit proto folder — the generator then uses only that folder and prunes build/, vcpkg_installed/, node_modules/, _legacy/, .git/, __pycache__/ subdirs.
Robot: Keyword with same name defined multiple times Generated against an old build before the Open Connection / Close Connection rename or the underscore-dedupe fix. Regenerate — current generator guarantees no internal collisions for any well-formed proto.
Generated keyword’s response is missing errorcode Bridge fix lives in reflect_client._msg_to_dict — if you see stripped fields, your bridge is stale. Restart it.
